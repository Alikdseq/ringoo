## Backend (Django + DRF)

### Архитектура

- Держи бизнес-логику в `apps/<domain>/(services.py|selectors.py|tasks.py)`; views должны быть тонкими.
- Сериализаторы — источник правды по контрактам: валидируют вход, формируют выход.
- Для списков: пагинация, фильтры, ordering — согласовывать с фронтом.

### API-ошибки

- Возвращай DRF-стиль ошибок: `{"detail": "..."}`
- Для доменных ошибок допускается `{"code": "...", "detail": "..."}` (как в orders).
- Статусы:
  - 400: валидация/бизнес-ошибка (недостаток остатков, пустая корзина).
  - 401/403: авторизация/права.
  - 404: не найдено.
  - 429: throttling (сообщение должно быть понятным).
  - 5xx: только для неожиданных ситуаций.

### Критичные интеграционные правила (e-commerce)

- **Корзина гость→логин**: при JWT-логине обязательно обеспечь перенос гостевой корзины в пользовательскую
  (иначе потеря конверсии). Любой рефактор auth/cart обязан сохранять этот сценарий.
- **Создание заказа**:
  - сервер пересчитывает суммы из БД; фронт не должен быть источником истины для цен.
  - поддерживай `X-Idempotency-Key` и повтор запроса без дублей заказа.
  - после успеха очищай корзину корректно.

### Тесты

- Для интеграционных потоков добавляй тесты, которые повторяют реальные запросы фронта.
- Любая правка в `auth/cart/orders` должна иметь тест на регрессию ключевых сценариев.
