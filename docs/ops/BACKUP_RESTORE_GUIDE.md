# Восстановление Ringoo из архива административной панели

Этот документ описывает восстановление из архива, созданного в админке (**Резервное копирование → Создать резервную копию и скачать**).

Связанные материалы:

- Операционные скрипты VPS: `docs/ops/BACKUP_AND_RESTORE.md`
- Краткая копия внутри архива: `RESTORE_GUIDE.md`

## 1. Что входит в архив

Типичное имя: `ringoo_backup_YYYY-MM-DD_HH-MM-SS.zip` или `.zip.enc`.

| Путь | Содержание |
|------|------------|
| `database/` | Дамп БД (`ringoo.sql` / SQLite / `dumpdata`) |
| `media/` | Содержимое `MEDIA_ROOT` (изображения, загрузки) |
| `manifest.json` | Метаданные, commit, состав, размеры |
| `checksums.txt` | SHA-256 файлов внутри архива |
| `RESTORE_GUIDE.md` | Краткая памятка |
| `.env.example` | Шаблон настроек **без секретов** |

**Не входит:** `.env`, ключи API, пароли БД, SSH-ключи, TLS-сертификаты.

## 2. Требования к серверу восстановления

- PostgreSQL той же мажорной версии, что в `manifest.json` → `database.server_version` (или совместимой).
- Python/Django и зависимости проекта (как в репозитории).
- Redis (если используется кэш/Celery).
- Достаточно места на диске: размер архива × 2 + БД.
- Доступ к `pg_restore` / `psql` (для SQL-дампа — `psql`).

Не восстанавливайте поверх production без отдельного плана и остановки записи.

## 3. Расшифровка (если файл `.enc`)

Формат: `RINGOO1` + salt(16) + nonce(12) + AES-256-GCM ciphertext.  
Пароль задаётся администратором при создании; **на сервере не хранится**.

Пример (Python, cryptography):

```python
from pathlib import Path
from apps.backups.services import decrypt_bytes
plain = decrypt_bytes(Path("archive.zip.enc").read_bytes(), "YOUR_PASSWORD")
Path("archive.zip").write_bytes(plain)
```

Пароль нельзя восстановить через поддержку Ringoo — храните его отдельно от архива.

## 4. Проверка целостности

```bash
unzip -t ringoo_backup_....zip
# после распаковки сверить checksums.txt (sha256sum -c checksums.txt)
```

Сверьте `sha256` файла архива с значением, показанным в админке при создании.

## 5. Восстановление базы

### PostgreSQL (предпочтительно)

```bash
# Новая пустая БД (пример)
createdb ringoo_restore
psql -d ringoo_restore -f database/ringoo.sql
```

Если в манифесте `format=django_dumpdata` — разверните схему миграциями, затем `loaddata`.

### SQLite

Скопируйте `database/ringoo_db.sqlite3` в путь `DATABASES.NAME` тестового окружения.

## 6. Восстановление медиа

```bash
rsync -a media/ /path/to/MEDIA_ROOT/
# или: cp -a media/. /path/to/MEDIA_ROOT/
```

## 7. Конфигурация

1. Скопируйте `.env.example` → `.env`.
2. Заполните **новые** секреты (`SECRET_KEY`, БД, YooKassa, Sber, SMTP и т.д.).
3. Укажите `DATABASE_URL` / параметры на **восстановленную** БД.
4. При необходимости выполните `python manage.py migrate` (если дамп со старой схемой и код новее — только после сверки).
5. Перезапустите web / celery / beat.

## 8. Проверка после восстановления

1. `GET /health/` — `healthy`.
2. Админ-вход (суперпользователь из дампа).
3. Каталог: товары и изображения.
4. Заказы / платежи: выборка последних записей без изменения статусов.
5. Остатки: сверка `Stock` / `StockMovement` на тестовых SKU.
6. Не запускайте реальные платежи и обмен с 1С без sandbox.

## 9. Независимое хранение (offsite вручную)

Скачивание ≠ offsite backup.

Рекомендации:

1. Копия на рабочем компьютере.
2. Копия на **отключённом** SSD/флешке.
3. Шифрование паролем при создании.
4. Периодический тест восстановления (не реже раза в квартал).
5. Политика сроков: например 30/90 дней + одна «замороженная» копия перед крупным релизом.

Автоматическая выгрузка в S3/облако **не подключена** без отдельного согласования.

## 10. Ограничения

- Параллельное создание нескольких архивов на сервере блокируется.
- Ссылка на скачивание одноразовая по смыслу токена + срок (`BACKUP_DOWNLOAD_TTL_HOURS`, по умолчанию 24 ч).
- Восстановление — ручная ops-процедура; кнопки «Restore» в админке нет (намеренно).
