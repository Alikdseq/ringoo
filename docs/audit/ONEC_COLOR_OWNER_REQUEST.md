# Запрос владельцу 1С: идентификаторы цветовых вариантов

**Статус:** требуется ответ владельца 1С / интегратора.  
**Контекст:** Ringoo Block 4 — сопоставление `ProductColor` с номенклатурой УТ11.

## Что уже есть в текущем XML (`Товары.xml`)

Каждая строка товара содержит:

- `code` — код номенклатуры (встречаются **одинаковые code на разных складах**);
- `parentCode`;
- `name` — часто включает цвет в тексте названия (`… Jet Black`, `… silver`);
- `type` / `typeID`;
- `sklad` / `skladID`;
- `series` / `seriesID`;
- `quantity`, `price`.

**Отсутствует:**

- GUID характеристики (`ХарактеристикаНоменклатуры`);
- отдельное поле цвета;
- SKU/артикул варианта, отличный от `code`, если вариант — характеристика;
- штрихкод варианта;
- явная связь «карточка сайта ↔ характеристика 1С».

## Почему нельзя сопоставлять по названию цвета

`Black` / `Черный` / `Jet Black` / `BlackGray` не гарантируют один вариант.  
Автоматическое угадывание цвета из `name` **запрещено** в архитектуре сайта.

## Рабочая гипотеза по текущим данным (требует подтверждения)

В выгрузке многие цветовые варианты выглядят как **отдельные коды номенклатуры** (`Товар.code`), а не как характеристики одной карточки.

Нужно подтвердить:

1. Является ли `Товар.code` стабильным идентификатором конкретного цветового варианта?
2. Или один `code` — это номенклатура, а цвет — характеристика с отдельным GUID, который **не попал** в XML?
3. Как отличать дубли `code` на разных складах (`skladID`) от разных вариантов?

## Что нужно добавить в API/XML для сайта

Предпочтительный вариант (приоритет сверху вниз):

1. **GUID характеристики** — стабильный UUID характеристики номенклатуры.  
2. **Пара** `nomenclatureGuid` + `characteristicGuid`.  
3. **Стабильный артикул варианта** (SKU), уникальный в пределах организации.  
4. Если варианты — отдельные номенклатуры: явный признак `isVariantOf` / `parentProductCode` + уникальный `code` варианта.

### Пример желаемой структуры (иллюстрация)

```xml
<Товар
  code="00-00000007"
  nomenclatureGuid="aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee"
  characteristicGuid="11111111-2222-3333-4444-555555555555"
  colorName="Jet Black"
  article="WATCH-S11-42-JB"
  barcode="4601234567890"
  skladID="..."
  seriesID=""
  quantity="1"
  price="79990"
/>
```

Поля `sklad*` / `series*` **не** должны использоваться как идентификатор цвета.

## Что уже подготовлено на сайте

- Поля `ProductColor.onec_code`, `onec_characteristic_ref`, `sku`, `barcode`, `mapping_status`.
- Статусы: `matched` / `unmatched` / `ambiguous` / `conflict` / `inactive`.
- Админ API ручного сопоставления.
- В payload заказа в 1С уходит `color`-matched `onec_code` / `characteristicRef` только при `mapping_status=matched`.
- Автоматический apply неоднозначных соответствий **не** выполняется.

## Просьба к владельцу 1С

1. Подтвердить модель: характеристика или отдельные коды.  
2. Предоставить тестовый XML/JSON с GUID характеристики или уникальным артикулом варианта.  
3. Указать, какие поля стабильны при переносе между базами.  
4. Не менять реальные остатки — достаточно тестовой выгрузки.
