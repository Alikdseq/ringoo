# Спецификация: цветовые варианты витрины ↔ 1С

Статус: **анализ + варианты**. Автоматическое «придуманное» соответствие **не внедрено**.

---

## 1. Фактическая модель на сайте

### ProductColor

- Таблица `products_productcolor`: FK `product`, `slug`, `label`, `hex`, опциональная цена.
- Назначение: витрина / UX / цена варианта.

### Корзина и заказ

- `CartItem` хранит цвет.
- `OrderItem`: FK `color` + снимки `color_label` / `color_slug` / `color_hex` (FUNC-011 / mig 0010).
- Checkout передаёт `color_id`; цена через `effective_price`.
- Reorder сохраняет цвет (INT-026 FIXED).
- Складской резерв/release привязан к **магазину заказа** и при серийности к **`onec_series_id`**, не к `ProductColor.pk`.

### Обмен заказа с 1С

`build_order_items_payload` (`integrations/onec/orders.py`):

- `productCode`, `quantity`, `amount`, `seriesId`
- **Поля цвета нет**

### Импорт каталога/остатков

XML (`parser.py`, fixtures): атрибуты `code`, `sklad`, `series`, `seriesID`, `quantity`, `price`.  
**Отдельного атрибута color нет.** Цвет иногда читается человеком из `name` (например «… black»), это не структурированное поле.

## 3. Возможные архитектуры сопоставления

### Вариант A — Один `onec_code` на цвет (рекомендуется при раздельных номенклатурах в 1С)

- В 1С у каждого цвета свой `code`.
- На сайте: либо отдельные `Product`, либо `ProductColor` с полем `onec_code` (потребует миграции).
- Заказ: `productCode` = код выбранного цвета → путаница цветов невозможна.
- **Нужно:** подтверждение, что в рабочей базе 1С так и есть.

### Вариант B — Одна номенклатура + цвет только на витрине

- `productCode` общий; цвет — UX.
- Риск: комплектовщик/1С не видят цвет, если он не в комментарии/названии.
- Допустимо только если цвет не влияет на складскую единицу.

### Вариант C — Цвет = series / характеристика 1С

- Путать `ProductColor` с `seriesId` **нельзя**: series в выгрузках — серийный учёт (IMEI/SN), не палитра.
- Если в конкретной базе 1С «серия» означает цвет — это **нестандарт** и требует явного решения владельца + примеров XML из production (не выдумывать).

### Вариант D — Расширение API SiteOrders

- Добавить в payload `colorLabel` / `colorSlug` (информативно).
- Не заменяет уникальный код, если склад различает варианты.

## 4. Примеры из локальных данных

- `backend/integrations/onec/fixtures/sample_products.xml` — `code` + `series`/`seriesID`, без color.
- Имена товаров могут содержать словесный цвет; парсер **не** выделяет его в сущность `ProductColor`.

Точного обязательного соответствия «slug цвета сайта = поле 1С» **в репозитории нет**.

---

## 5. Целевые свойства (acceptance)

1. Два цвета одного товара не смешиваются в заказе/корзине/reorder — **на сайте уже**.
2. Резерв/release относится к той же складской линии (`store` + series) — **на сайте уже**.
3. Обмен с 1С не теряет идентификатор **складского** варианта — зависит от того, равен ли он `productCode`/`seriesId`.
4. Импорт не создаёт дубликаты — правила `importer.py` по `onec_code` / SKU; цвет их не дублирует сам по себе.

## 6. Решения владельца / 1С-разработчика

1. В рабочей 1С цвет — это **отдельный code**, часть **наименования**, или **характеристика**?
2. Нужно ли поле цвета в JSON заказа для менеджеров 1С?
3. Добавлять ли `ProductColor.onec_code` на сайте?
4. Есть ли дубли `code` из‑за складов (уникальность code+sklad)?

До ответов статус интеграции цвета: **NEEDS BUSINESS DECISION** (INT-010).  
Код витрины/заказа по цвету — **FIXED** в рамках сайта.
