# Аудит интеграции фронтенда и бэкенда (Ringoo)

**Дата аудита:** 29 марта 2026  
**Стек:** Django REST Framework + Next.js (App Router, TypeScript), TanStack Query, Axios, JWT (и опционально HttpOnly-куки).

**Источники:** `ТЗ.txt`, `ARCHITECTURE.md`, `PLAN.md`, `docs/API.md`, код `backend/`, `frontend/`.

---

## Общее резюме

Интеграция в целом выстроена осознанно: единый базовый URL API, Axios с refresh по 401, TanStack Query с разумными дефолтами (`retry: 1` для queries), `X-Idempotency-Key` для создания заказа, явная передача позиций заказа при `from_cart: true` для обхода рассинхрона cookie между origin — это сильные стороны.

Однако обнаружены **критические разрывы** между ожидаемым поведением e‑commerce и фактической реализацией: главное — **гостевая корзина не объединяется с корзиной пользователя при входе через JWT**, хотя в коде бэкенда предусмотрена функция слияния, привязанная к сигналу сессионного логина. Дополнительно есть расхождения документации API с маршрутизацией, демо-логика промокода на чекауте и отсутствие клиентского Sentry.

**Итоговая оценка готовности связки «как единый организм»:** требуется доработка критических пунктов перед продакшеном; остальное — систематическое усиление контрактов и наблюдаемости.

## Проблемы по модулям

### Аутентификация и сессия

#### Критичная: гостевая корзина не сливается при входе по JWT

- **Где:** `backend/apps/cart/services.py` (`merge_guest_cart_into_user`), `backend/apps/cart/signals.py` (сигнал `user_logged_in`), `backend/apps/users/views.py` (выдача JWT без `django.contrib.auth.login`).
- **В чём проблема:** После добавления товаров в корзину как гость корзина привязана к `session_key`. При входе через `POST /api/v1/auth/` пользователь аутентифицируется JWT, но `Cart.get_or_create_cart` для авторизованного пользователя возвращает **отдельную** корзину по `user`, не перенося товары из гостевой. Слияние вызывается только из сигнала `user_logged_in`, который при типичном SPA-логине через JWT **не срабатывает**.
- **Почему важно:** Пользователь теряет корзину сразу после логина — прямой удар по конверсии и доверию.
- **Решение:** На бэкенде после успешной аутентификации в `CustomTokenObtainPairView` (и при необходимости после регистрации) явно вызывать `merge_guest_cart_into_user(request, user)` при наличии `request.session.session_key`, либо вынести слияние в middleware/хук первого запроса с JWT + session cookie. Альтернатива: эндпоинт «синхронизировать корзину» с фронта после логина. Покрыть интеграционным тестом: гость с товарами → JWT login → `GET /cart/` содержит те же позиции.

```python
# Идея: после serializer.is_valid() и перед выдачей токена
from apps.cart.services import merge_guest_cart_into_user
merge_guest_cart_into_user(request, serializer.user)
```

### Корзина

#### Высокая (следствие критичной): после логина фронт не делает `invalidateQueries` для корзины

- **Где:** `frontend/src/app/login/page.tsx`, `frontend/src/app/register/page.tsx` — после успеха только `AUTH_ME_QUERY_KEY`.
- **Проблема:** Даже после исправления слияния на бэке полезно инвалидировать `['cart']`, чтобы UI подтянул актуальные данные.
- **Решение:** `queryClient.invalidateQueries({ queryKey: ['cart'] })` после успешного входа/регистрации (и при смене режима auth cookies).

#### Средняя: дублирование инвалидации в `useAddToCart`

- **Где:** `frontend/src/lib/hooks/useCart.ts` — `onSuccess` делает `setQueryData`, а `onSettled` всегда `invalidateQueries`.
- **Почему:** Лишний запрос к серверу на каждое добавление; не ошибка, но нагрузка при массовых действиях.
- **Решение:** Оставить один источник истины (только invalidate или только setQueryData + refetch при ошибке).

### Оформление заказа (checkout)

#### Высокая: отображаемая скидка по промокоду не совпадает с суммой заказа на сервере

- **Где:** `frontend/src/app/checkout/page.tsx` — `promoDiscount`, `finalTotal`, `total_amount` в payload; `backend/apps/orders/serializers.py` — `OrderCreateSerializer.validate()` пересчитывает `total_amount` из цен каталога.
- **Проблема:** В интерфейсе указано, что это демо (5%), но в payload всё равно уходит `total_amount`, которое на сервере **перезаписывается** расчётом из БД. Пользователь видит одну сумму, в заказе и письмах — другую.
- **Решение:** Интегрировать реальные промокоды через API (`/promocodes/` или аналог), либо убрать демо-скидку из UI до готовности бэкенда. Не показывать «итого к оплате» со скидкой, если сервер её не применяет.

#### Высокая: согласие на рассылку на чекауте не передаётся в API

- **Где:** `checkout/page.tsx` — состояние `consentNewsletter`; при отправке заказа в payload не попадает.
- **Проблема:** Юридически и по продукту чекбокс не имеет эффекта (в отличие от регистрации, где есть `consent_marketing`).
- **Решение:** После успешного заказа вызывать `PATCH /auth/me/` с `marketing_opt_in: true` при отмеченном чекбоксе, либо расширить создание заказа полем согласия на сервере.

#### Средняя: `createOrder` типизирован как `unknown`

- **Где:** `frontend/src/lib/api/services/orders.service.ts`.
- **Решение:** Ввести интерфейс `CreateOrderPayload`, совпадающий с `OrderCreateSerializer` (включая опциональные поля), и использовать его в форме.

### Каталог и поиск

#### Средние: в целом хорошо

- Debounce поиска в каталоге (250 ms) и в шапке (300 ms), `staleTime` для автодополнения — соответствует требованиям производительности.
- Infinite query через `useInfiniteQuery` с пагинацией — без лишних запросов при ререндере.

#### Низкая: карточка товара — нет явной блокировки кнопки на время мутации

- **Где:** `frontend/src/components/features/products/ProductCard.tsx` — можно использовать `addToCartMutation.isPending` для `disabled` на кнопке «В корзину».

### Личный кабинет и заказы

#### Средняя: после создания заказа редирект на `/orders` без страницы успеха с номером

- **Где:** `checkout/page.tsx` — `router.push('/orders')`.
- **Проблема:** UX: пользователь не видит явного подтверждения с номером заказа сразу (есть отдельные success-роуты для части сценариев — проверить единообразие).
- **Решение:** Редирект на `/orders/{id}/success` или показ toast с номером из ответа `POST /orders/`.

**Положительно:** После заказа вызываются `invalidateQueries` для `['cart']` и `['orders']` — список заказов обновляется.

### Бонусы

#### Высокая: документация и код расходятся

- **Где:** `docs/API.md` описывает `GET /api/v1/bonus/`; в `backend/config/api_urls.py` маршрут `bonus/` закомментирован с пояснением «публичный API временно отключён».
- **Проблема:** Риск обращения фронта или сторонних клиентов к несуществующему endpoint.
- **Решение:** Обновить `docs/API.md` и схему OpenAPI; на фронте не вызывать bonus до включения (сейчас прямых вызовов в `src/` не обнаружено — ок).

### Контент, CRM, промо

- Интеграция по паттерну сервис + `useQuery` выглядит согласованной; отдельных критичных несоответствий по просмотренным вызовам не выявлено.

### Обработка ошибок и устойчивость

#### Средняя: нет специальной ветки для HTTP 429 в `getFriendlyErrorMessage`

- **Где:** `frontend/src/lib/errors.ts`.
- **Проблема:** При throttling пользователь получает общее сообщение вместо явного «слишком много запросов».
- **Решение:** Добавить ветку `status === 429` с текстом, согласованным с бэкендом.

#### Средняя: повторы только через React Query (1 раз), без retry для 5xx на Axios

- **Где:** `frontend/src/lib/api/client.ts` — retry только при 401 + refresh.
- **Решение:** Для идемпотентных GET опционально retry в interceptor или оставить как есть (текущий `retry: 1` в QueryProvider частично покрывает).

#### Средняя: отсутствует Sentry (или аналог) на фронтенде

- **Где:** в `frontend/src` нет интеграции Sentry (в отличие от упоминания в `PLAN.md`).
- **Решение:** Подключить `@sentry/nextjs`, DSN через env, не коммитить секреты.

### Безопасность взаимодействия

- **CORS:** В `base.py` настроены `CORS_ALLOW_HEADERS` с `x-idempotency-key`, `CORS_ALLOW_CREDENTIALS` — корректно для cookie-сессии гостя.
- **CSRF:** Для JWT-запросов с `Authorization` CSRF не требуется; эндпоинты токенов помечены `csrf_exempt` — соответствует задокументированной модели угроз в `users/views.py`.
- **Секреты на клиенте:** Используются только `NEXT_PUBLIC_*` (в т.ч. ключи карт — ожидаемо публичные для JS API); серверные секреты в репозитории не искались — **не** выносить `SECRET_KEY`/платёжные ключи в `NEXT_PUBLIC_`.
- **HTTPS:** В продакшене `JWT_COOKIE_SECURE`, `CSRF_COOKIE_SECURE` — через env; документировать обязательность HTTPS для прода.

### Типизация и контракты API

- **Корзина:** `product` в POST соответствует `CartItemCreateSerializer`; в `docs/API.md` указано `product_id` — **низкая** расхождение документации.
- **Категории:** `GET` может возвращать массив или paginated — фронт в `getCategories` обрабатывает оба варианта — хорошо.
- **Заказы:** Поля `Order` в `frontend/src/types/api.ts` в основном согласованы с `OrderSerializer` (включая `has_rating`).

## Рекомендации по процессу

1. **OpenAPI как источник правды:** Уже есть `/api/schema/` — генерировать TypeScript-типы (openapi-typescript, openapi-fetch) в CI и падать сборку при расхождении с ручными правками.
2. **Контрактные тесты:** Минимальный набор pytest + запросы к API с теми же телами, что собирает фронт; на фронте — MSW или e2e (Playwright) против mock или staging.
3. **Регрессия интеграции:** Чек-лист перед релизом: гость → корзина → логин → корзина сохранена; оформление заказа → корзина пуста → заказ в списке; 401 → refresh → повтор запроса.
4. **Единый changelog API:** При отключении маршрутов (как `bonus/`) сразу обновлять документацию и фронтовый слой.

## Заключение

Архитектурные решения (JWT + cookie для гостя, идемпотентность заказа, TanStack Query) выбраны уместно. Для «эталонной» связки Django + Next.js необходимо устранить **разрыв жизненного цикла корзины при JWT-аутентификации** и привести в соответствие демо-промо и серверный расчёт сумм. Остальное — усиление типобезопасности, документации и наблюдаемости.
