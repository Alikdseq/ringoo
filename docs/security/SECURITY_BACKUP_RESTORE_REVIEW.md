Дата: 2026-11-07. Скрипты не запускались. Архивы не создавались и не удалялись. S3 не вызывался. Рабочая база не восстанавливалась.

## Что умеет репозиторий

Два контура.

1. Скрипты на хосте. `scripts/backup-set.sh` снимает `pg_dump` из контейнера `ringoo_db` и tar media-тома, пишет `set_<id>/MANIFEST.txt`, проверяет gzip и считает SHA256. Age — только при `AGE_RECIPIENT`. Иначе дамп остаётся открытым (RINGOO-INF-004). В S3 скрипт не загружает. Старые `set_*` старше `BACKUP_KEEP_DAYS` (14) удаляются с диска. `scripts/backup-db.sh` пишет один открытый `.sql.gz`. `scripts/backup-media.sh` и `scripts/restore-media.sh` лежат рядом и в этом блоке читались как отдельные шаги, не как доказательство последнего успешного прогона.

2. Django `apps/backups`. Архив — zip с дампом, media, `manifest.json` и `checksums.txt`. Секреты `.env` в комментарии к сервису исключены. Шифрование AES-GCM, если задан `BACKUP_ENCRYPTION_KEY`. Скачивание — admin API только суперпользователя, с токеном и сроком. Выгрузка в S3: `put_object` с `ACL=private`, затем `head_object` и сравнение размера. Отдельная проверка SHA256 есть в `apps/backups/offsite.py` при verify. Повторы boto3: `max_attempts: 3`. Флаги `BACKUP_OFFSITE_ENABLED` и `BACKUP_SCHEDULED_ENABLED` по умолчанию ложные. Пока их не включили в env, суточный beat backup не ставится и бакет не используется.

Реальный бакет по коду не определяется. Наличие адаптера не означает, что объекты в нём есть.

Публичного URL архива для покупателя нет. Удаление объекта S3 есть функцией `delete_object` для кода приложения, не для анонимного HTTP. Политика бакета (Block Public Access) с сервера не читалась — NOT TESTED.

## Restore

`scripts/restore-db.sh` заливает gzip в `psql` того же контейнера. Флаг `--drop` стирает таблицы `public` без проверки, что это не production. Отката нет. Версия приложения и схема до заливки не сравниваются. После скрипт советует `make migrate`.

Встроенная памятка `backend/apps/backups/RESTORE_GUIDE_EMBEDDED.md` говорит проверить `checksums.txt`. Это инструкция, не журнал проведённого восстановления.

Доказательства успешного restore drill в этом блоке нет. Старые отчёты в `docs/audit/` могут описывать прошлые прогоны. Этот аудит их за факт текущего восстановления не принимает и drill не повторял.

## RPO и RTO

В `docs/ops/BACKUP_AND_RESTORE.md` написано: рекомендуемые RPO ≤ 24 часа и RTO ≤ 4 часа **не утверждены** владельцем. Подставлять их как действующие нельзя.

По конфигурации, если включены и cron `backup-set`, и `AGE_RECIPIENT`, и внешняя копия, интервал потери — около суток. Включено ли это на сервере — NOT TESTED. Время восстановления не измерялось.

Нужно хранить: базу (заказы, пользователи, каталог) и media. Конфиги env в архив сознательно не кладутся: без отдельной копии секретов подъём на новом хосте не завершится. Эту копию скрипт не делает.
