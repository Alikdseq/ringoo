# План исправлений

Срез после блока 8. Исправления INV-001, INV-002 и PAY-001 внесены в код и проверены на SQLite с mock. Живые ЮKassa, 1С, PostgreSQL и VPS не проверялись. Это не допуск к запуску.

Дата: 2026-11-07.

## Сразу, до следующей выкладки фронтенда

1. RINGOO-FE-002. В `json-ld.tsx` сериализовать JSON-LD одной функцией, которая заменяет `<` на `\u003c` (достаточно закрыть выход из `<script>`). Не чинить отдельные поля. Проверка: изолированный HTML, как в реестре, больше не создаёт второй classic script. Затем тестовый товар только на копии базы.
2. RINGOO-FE-001. Общая функция `safeNextPath`: один ведущий `/`, запрет `//`, `/\`, `\`, схема и обратный слэш. Подключить в `/login`, `/register`, `/admin/login`. Проверка: `https://example.invalid/`, `//example.invalid/`, `/\\example.invalid`, `///example.invalid` оставляют пользователя на сайте. Свой `/profile` и `/admin/orders` работают. `javascript:` по-прежнему не нужен как единственная защита.

Оба пункта маленькие и не меняют API.

## Сразу по backend, вместе с пунктами 1–2

2a. RINGOO-API-001. Удалить `author_phone` из `ArticleSerializer` и `NewsSerializer`. Проверка на SQLite: карточка статьи больше не содержит телефон.
2b. RINGOO-API-002. На публичных `ArticleViewSet` и `NewsViewSet` не читать `is_published` из query. Черновики только в admin API. Проверка: `?is_published=false` возвращает тот же набор, что и список без параметра, черновика в нём нет.

## До staging

3. RINGOO-FE-003. В `logout` очищать кэш запросов (`queryClient.clear()` или точечно личные и админские ключи). В ключ `orders`, `addresses`, `wishlist`, `order` добавлять id пользователя. Проверка двумя синтетическими пользователями в одной вкладке без перезагрузки: адреса checkout и заказы профиля не пересекаются.
4. Не выключать cookie-режим на staging (`NEXT_PUBLIC_USE_AUTH_COOKIES` не равен `0`). Иначе FE-002 читает JWT из `localStorage`.
5. Платёжный переход (FE-NOTE-04) не чинить вслепую на клиенте, пока блок 8 не покажет, какой host вообще имеет право вернуть API. Если API может вернуть произвольный URL — резать и на сервере, и на клиенте allowlist.

## До коммерческого запуска

6. Сузить CSP: убрать `'unsafe-eval'`, затем по возможности `'unsafe-inline'` (nonce или hash для скрипта темы и Яндекс.Карт). Это не замена пункта 1. Пока FE-002 открыт, CSP его не держит.
7. Гостевой токен заказа не оставлять доступным любому скрипту дольше, чем нужно для оплаты. Оценка вместе с блоком 5.
8. Source maps браузера не включать (`productionBrowserSourceMaps` не ставить). Каталог `.next/server` не публиковать рядом со статикой. Сейчас статика карт не содержит; это сохранить.

## Можно отложить

- Заглушки новостей и блога, пока они не рендерят HTML из API. Когда появятся, сразу закладывать текст или санитайзер, не `dangerouslySetInnerHTML` сырого HTML.
- Referrer-ограничение ключа Яндекс.Карт в кабинете Яндекса. На безопасность сессии магазина не влияет.
- Follow `next` в sitemap. Имеет смысл, когда появится недоверенный источник пагинации. Сейчас `next` строит свой API.
