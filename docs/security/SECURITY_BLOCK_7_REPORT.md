# Блок 7. Платежи, 1С, склад

Дата: 2026-11-07. Код, настройки, контейнеры и рабочая база не менялись. Реальные ЮKassa, 1С, публичный домен и VPS не вызывались.

Изоляция прогона: `DJANGO_SETTINGS_MODULE=config.settings.test`. До создания данных движок был `django.db.backends.sqlite3`, имя `:memory:`. После `DiscoverRunner.setup_databases()` имя стало `file:memorydb_default?mode=memory&cache=shared`, поставщик `sqlite`. Сеть из заглушки ЮKassa не открывалась.

## Что подтверждено на SQLite

Схема оплаты в коде: заказ → резерв в выбранном магазине при создании → `POST /api/v1/orders/{id}/pay/` → `initiate_yookassa_payment` → редирект на `confirmation_url` → `POST /api/v1/payments/yookassa/webhook/` → `GET /payments/{id}` → при совпадении суммы, валюты и metadata платёж `paid`, заказ `new → confirmed`. Страница возврата сама оплату не ставит.

- Сумма в заглушку ушла `1500.00` из `Order.total_amount`. Тело `{"amount":"1.00","status":"paid"}` при выключенной ЮKassa дало 503 `payments_disabled` и ноль платежей.
- Чужой пользователь на `POST /pay/` получил 403.
- Повтор при открытом платеже вернул тот же ряд (`reused=True`, count=1).
- Уже `paid` — `already_paid`. Отменённый заказ — `order_cancelled`.
- Тело webhook `succeeded` при GET `pending` оставило платёж `pending` и заказ `new`.
- Сумма `1.00` и валюта `USD` дали `needs_review`, заказ остался `new`.
- Совпадающий GET: один `paid`, заказ `confirmed`. Повтор webhook второй `paid` не создал.
- Неизвестный id: обработчик вернул пусто.
- Оплата отменённого заказа при `LATE_ONLINE_PAYMENT_POLICY=manual` оставила заказ `cancelled`, платёж `needs_review`.
- Полный refund по одному id идемпотентен. Заказ остался `confirmed` (INV-002).
- `new → completed` и статус `paid` у заказа отклонены.
- Два последовательных `reserve_atomic` на остаток 1: второй вернул false, резерв остался 1.
- XXE отклонён (`EntitiesForbidden`). Dry-run число товаров не изменил. Apply записал цену `-10` и остаток `0` (INV-001).
- `http://127.0.0.1/razrab/hs` нормализатор принял. `ut11_test` отклонил. Это настройка базового URL, не ввод покупателя (BE-NOTE-06).

`RETURNS_ENABLED` и `ONE_C_API_ENABLED` в тестовых настройках выключены. Флаг ЮKassa включался только внутри процесса после проверки «провайдер выключен».

## Что этим блоком не доказано

Гонка двух покупателей на PostgreSQL. Файл `backend/tests/test_concurrency_postgres.py` сам требует `RINGOO_TEST_POSTGRES=1` и отдельную базу. Он не запускался. SQLite `select_for_update` не считается доказательством блокировки.

Живой webhook, песочница ЮKassa, тестовая публикация 1С, таймаут реального API, два webhook в один момент, возврат денег у провайдера.

## Ответы

1. Подмена суммы покупателем — NO. Сумма берётся из заказа. На SQLite в шлюз ушло `1500.00`.
2. Оплата чужого заказа — NO. `POST /pay/` пользователя B вернул 403.
3. Повторная оплата уже оплаченного — NO. Код `already_paid`. Уникальный частичный индекс `payments_one_paid_per_order`.
4. Дубли платежей — NO для открытого платежа: повтор переиспользует ряд. Два одновременных `pay` на PostgreSQL — NOT TESTED.
5. Подлинность webhook — PARTIAL. Подписи нет, список IP по умолчанию пуст (PAY-001). Оплата ставится только после GET.
6. Поддельный webhook — NO. Тело `succeeded` при GET `pending` заказ не оплатило.
7. Сумма и валюта — YES в коде сверки и на SQLite: несовпадение даёт `needs_review`.
8. Повтор webhook — YES на SQLite: один `paid`.
9. Повторный возврат одного платежа — NO для того же `refund_id`. Сумма сверх оплаченной в `initiate_money_refund` отклоняется по коду. Провайдер не вызывался. Заказ при этом не закрывается (INV-002).
10. Права на чужой возврат — PARTIAL. При выключенном флаге маршрут закрыт. При включении любой `is_staff` проходит во владельцы (API-003, блок 4). В этом прогоне флаг не включался.
11. Синхронизация 1С — PARTIAL. Apply с API запрещён при выключенном флаге и требует `confirm=true` и группу `ringoo_catalog`. Замок — `cache.add`; в тестах кэш DummyCache и на проде не проверялся. Живой вызов NOT TESTED.
12. XXE — YES, парсер `defusedxml` отклонил внешнюю сущность.
13. Порча каталога кривым XML — PARTIAL. Массового удаления нет. Одна позиция получила отрицательную цену и нулевой остаток (INV-001).
14. Dry-run — YES на этом XML: число товаров не изменилось.
15. Повторный apply — PARTIAL. Повтор после завершения разрешён. Параллельный apply удерживается замком только если кэш его хранит. На Redis NOT TESTED.
16. Синхронизация и резерв — YES, код может записать `quantity` ниже текущего `reserved_quantity` и резерв не снимает. На SQLite этот случай с ненулевым резервом не гонялся.
17. Последняя единица — PARTIAL. Последовательно на SQLite второй резерв не проходит. Одновременно на PostgreSQL NOT TESTED.
18. Двойное списание — NO в пути оплаты: успех webhook количество `Stock.quantity` не уменьшает, резерв берётся при создании заказа. Повтор webhook резерв не удваивает. Гонка создания двух заказов NOT TESTED.
19. Переходы — YES по таблице FSM и двум запрещённым переходам на SQLite. Полный обход всех рёбер не делался.
20. Нужны отдельные разрешения: песочница ЮKassa без боевого ключа, тестовая публикация `/razrab/hs/`, гонка `test_concurrency_postgres.py` на пустой базе `ringoo_test`, возврат при `RETURNS_ENABLED` только на SQLite.

Подтверждённые проблемы этого блока: INV-001, INV-002, PAY-001. Ранее открытые FE, API и AUTH не закрывались.

Передача дальше. Платёжный контур по коду не доверяет телу webhook и сумме из браузера. Это не готовность магазина: нет прогона на PostgreSQL, нет живой ЮKassa и нет живой 1С. Общей оценки и допуска к запуску нет.
