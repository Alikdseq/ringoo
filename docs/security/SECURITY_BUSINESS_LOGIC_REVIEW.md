# Разбор бизнес-логики заказов, каталога и оплаты

Дата: 2026-11-07. Платежи в ЮKassa не создавались. Заказы в рабочей базе не менялись. Создание заказа на SQLite не вызывалось: пересчёт суммы прочитан в `OrderCreateSerializer.validate` и в `OrderListCreateView.post`.

## Создание заказа

`POST /api/v1/orders/` разрешён без входа. Это задумано: гостевой заказ. Владелец — `request.user`, если он аутентифицирован, иначе `user` пустой. Поля `user_id` в `OrderCreateSerializer` нет.

Цена позиции берётся из `ProductColor.effective_price()` или `Product.price`. Клиентский `price` в расчёт не идёт. Если `expected_unit_price` не совпал и нет `accept_price_changes`, ответ 400 `price_changed`. После разрешения позиций код ставит `delivery_cost = 0`, `bonus_used` остаётся 0 при выключенных бонусах, `total_amount` равен сумме позиций. Числа из тела на этом шаге затираются.

Товар должен быть активен. Количество в сериализаторе ограничено. Магазин для самовывоза — активная точка, не склад. Новый заказ с оплатой «банковский перевод» отклоняется. Адрес в заказе — JSON, который ввёл клиент, а не id чужого `DeliveryAddress`. Подменить сохранённый адрес другого пользователя этим полем нельзя. Вписать произвольный текст адреса в свой заказ можно.

Идемпотентность: повтор с тем же ключом может вернуть сохранённый ответ из кэша. Отдельный разбор гонок остатка при двух одновременных заказах в этом блоке не выполнялся. Резерв в view идёт внутри `transaction.atomic` после пересчёта. Гонку двух транзакций по одному остатку динамически не воспроизводили. Статус: не проверено.

Отрицательная сумма отсекается в `validate_total_amount` и затем всё равно заменяется серверной суммой. Нулевая серверная сумма возможна только если каталог отдал 0. Онлайн-оплата такой суммы в `yookassa_service` отклоняется (`amount <= 0`).

## Изменение заказа

У покупателя нет PATCH состава, количества, адреса, способа оплаты, суммы, статуса и владельца. Отмена — `POST /orders/{id}/cancel/`: владелец или guest token, не «любой staff». Статусы только `new` и `confirmed`. Оплаченный заказ этим путём не отменяется.

Админ `PATCH /admin/orders/{id}/` принимает одно поле `status`. Переходы заданы в `ALLOWED_TRANSITIONS`: new → confirmed или cancelled; confirmed → in_progress или cancelled; in_progress → completed или cancelled; completed и cancelled — пусто. Перехода в оплаченное состояние через это поле нет. Оплата меняет заказ в сервисе платежа после сверки с ЮKassa, не из тела покупателя.

Повторная оплата. `evaluate_order_payment_eligibility` пускает только `payment_type=online` и статусы заказа `new` или `confirmed`, и не пускает, если платёж уже в `paid`, `needs_review`, `reversed`, `refunded`. Повторный активный платёж возвращает уже выданный `confirmation_url`, а не новый произвольный. Вызов в ЮKassa в этом блоке не делался. Вывод по коду: оплатить чужой заказ нельзя, сумму в запросе оплаты передать нельзя, оплаченный и отменённый заказ в initiate не проходит.

`form_url` в ответе — значение, которое вернула ЮKassa, и оно read-only. Адрес возврата (`return_url`) собирается из `YOOKASSA_RETURN_URL` или `FRONTEND_URL` и id заказа. `request.get_host()` там нет.

## Каталог и цепочка FE-002

Путь данных такой.

1. Источник записи: `PATCH /api/v1/admin/products/{id}/patch/` и создание товара, группы `ringoo_catalog`, либо исходящая синхронизация 1С, если она включена. Аноним и покупатель write-маршрутов каталога не имеют.
2. Сериализатор пишет `title`, `brand`, `description`, `short_description`, `meta_title`, `meta_description`, цену, sku, категорию, `is_active`. У товара с `onec_code` управляемые 1С поля отклоняются. `onec_code` клиенту не отдаётся на запись.
3. Модель хранит строки как есть.
4. Публичный GET отдаёт их покупателю.
5. Фронтенд кладёт название, бренд, sku и короткое описание в JSON-LD без замены `<`. Это RINGOO-FE-002.

Покупатель без группы каталога эту строку записать не может. Сотрудник `ringoo_catalog` может. Обхода группы через другой публичный endpoint не найдено. Подмена цены покупателем на заказе закрыта пересчётом. Подмена цены товара — действие каталожной группы, не покупателя. Подмена владельца товара не применима: у товара нет владельца-покупателя.

Картинки товара: `upload_to` подставляет uuid, расширение чистится. Отдельный `validate_image_bytes` в admin view не вызывается. Django `ImageField` проверяет файл через Pillow. SVG как изображение Pillow не принимает. Разбор вредоносных файлов в этом блоке не загружался.

## Host и абсолютные URL

На SQLite запрос с `HTTP_HOST: evil.example` получил 400 `DisallowedHost`. Django не строит `next` пагинации, пока host не в `ALLOWED_HOSTS`. `USE_X_FORWARDED_HOST` в настройках не задан, значит заголовок `X-Forwarded-Host` не становится host. `X-Forwarded-Proto` учитывается только если включён `TRUST_PROXY` (production).

Ссылки сброса пароля и восстановления гостевого заказа берут `FRONTEND_URL`. Возврат ЮKassa — настройка, не Host запроса.

Живой nginx и список `ALLOWED_HOSTS` на VPS не смотрелись. Если в список попадёт лишний host, пагинация сможет отдать абсолютный `next` на него. Это не подтверждено для production.

## SSRF

Покупатель и сотрудник не передают URL, по которому Django пойдёт во внутреннюю сеть.

- 1С: базовый URL из настроек, redirect только на тот же host, тело ответа до 20 МиБ. Запрета частных адресов нет. Если в настройке указан внутренний host, воркер на него пойдёт. Это конфигурация.
- ЮKassa и Сбер: фиксированные клиенты, не URL из заказа.
- Геокодер: host `https://geocode-maps.yandex.ru/v1/`, адрес пользователя уходит параметром `geocode`.

Запросов на metadata и на частные адреса не было.

## Ошибки и лимиты

В production `DEBUG` запрещён модулем настроек. Health не возвращает текст исключения. Неверный host на тесте дал 400 без тела настроек. Трассировки production не снимались.

Лимиты DRF заданы в `REST_FRAMEWORK`: вход 5/мин, регистрация 5/час, заказ 10–20/час, оплата 20–60/час, webhook ЮKassa 60/мин, трек 5/мин, TOTP 5/мин. Axes: 8 неудач, блокировка по имени и IP на час. Обход сменой `X-Forwarded-For` зависит от `AXES_IPWARE_PROXY_COUNT` и от того, как proxy выставляет `REMOTE_ADDR`. Нагрузочных запросов не было. Для production-прокси статус лимитов: не проверено.
