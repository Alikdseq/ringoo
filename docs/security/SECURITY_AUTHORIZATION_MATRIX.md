Дата: 2026-11-07. Проверка серверных классов, не кнопок витрины. Два контура не смешиваются: `/api/v1/admin/` (JWT, staff, группа `ringoo_*`, TOTP-claim при включённом OTP) и Django Admin (сессия, `is_staff`, в production `OTPAdminSite`).

Динамика блока 4: SQLite, OTP в test settings выключен. Блок 5 дополнил матрицу прямыми HTTP на той же SQLite, отдельно с `ADMIN_OTP_ENABLED=True` в процессе теста. Рабочие settings не менялись.

Проверено по `get_queryset` / явному фильтру. SQLite отмечен отдельно.

| Объект | GET чужого | PATCH чужого | DELETE чужого | Custom action |
|---|---|---|---|---|
| Заказ | 404. SQLite | маршрута правки нет | нет | cancel и pay требуют владельца или guest token. Staff чужой заказ на этих view не открывает |
| Адрес | queryset по user, чужой id не находится | то же | то же | нет |
| Избранное | свой список | нет | только своя запись | нет |
| Корзина | своя сессия | позиция ищется как `pk` и `cart` | то же | clear чистит свою |
| Платёж | статус только после `_can_access_order` | суммы в теле нет | нет | pay чужого по коду 403. HTTP в ЮKassa не отправлялся |
| Возврат | список по user. Карточка: владелец, а при включённом флаге ещё любой staff | клиентского PATCH нет | нет | create по чужому заказу: 403, кроме staff при включённом флаге |

Гостевой заказ с `user_id` guest token не открывает. Номер и телефон дают урезанный статус, не адрес и не позиции.

## Ответы на вопросы о повышении прав

1. Аноним на admin API. Нет. SQLite: 403.
2. Покупатель на endpoint сотрудника. Нет для `/api/v1/admin/`.
3. Сотрудник одной группы на endpoint другой. На SQLite каталог получает 403 на заказах, пользователях, CRM, контенте, магазинах, отчётах, бэкапах и возвратах. Свои товары — 200. Заказы не открывают каталог. Контент не открывает заказы. CRM не открывает заказы. Сотрудник без группы — 403 на всех проверенных admin URL, включая дашборд. Две группы `ringoo_catalog` и `ringoo_orders` открывают оба своих контура и по-прежнему 403 на пользователях. Дашборд — исключение: 200 у любой группы `ringoo_*` (RINGOO-AUTH-003).
4. Покупатель меняет свою роль. Нет.
5. `is_staff` через serializer покупателя. Нет. Поле не принимается.
6. Группа через API покупателя. Нет. Через admin users — только superuser.
7. Обход роли прямым HTTP мимо UI. Для admin API нет: проверка на view, не на кнопке. Для черновиков контента обход есть: query `is_published=false` (RINGOO-API-002).
8. TOTP на защищённых admin-операциях. Да, класс `AdminMfaVerified` на каждом `admin_permissions`, если `ADMIN_OTP_ENABLED`. В production модуль требует OTP. В test settings флаг выключен, и класс тогда возвращает True. Это не «только фронтенд».
9. TOTP только на фронтенде. Нет.
10. Старый JWT после выхода. Refresh попадает в blacklist при logout. Access живёт до истечения. Отдельной проверки blacklist access нет.
11. Токен заблокированного пользователя. На SQLite access, выпущенный до `is_active=False`, на следующем запросе получает 401 `user_inactive`. Новый access из refresh тоже получает 401. Сам refresh endpoint при этом отвечает 200 (RINGOO-AUTH-002). Пароль после блокировки — 401.
12. Состояние пользователя на запросе. Для JWT — да, через `get_user`. Для гостевого заказа пользователя нет. Для admin MFA claim берётся из токена и не перепроверяет секрет TOTP на каждом вызове после verify. Повторная проверка кода — блок 5.

## Mass assignment

| Поле | Покупатель | Admin update |
|---|---|---|
| `is_staff`, `is_superuser`, `groups`, `user_permissions` | не в сериализаторах. PATCH me пишет только согласие | `is_staff` и `groups` только superuser. `is_superuser` и `user_permissions` в сериализаторе нет |
| `role` | поля нет | поля нет. Роль — это группы Django |
| `status` заказа | клиентского PATCH нет | только `ringoo_orders`, FSM |
| `user` заказа | берётся из `request.user`, не из тела | admin PATCH статус, не владельца |
| цена, итог, доставка, бонус | принимаются и заменяются в `validate` | цена товара — `ringoo_catalog`, не покупатель |
| `onec_code` товара | нет | read-only |
