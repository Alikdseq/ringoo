# Программа аудита безопасности Ringoo

- Документ: программа проверки до подтверждения уязвимостей (BLOCK 2).
- Дата: 2026-11-07.
- Объект: исходный код `C:\ringoo` и локальные конфигурации. Живой VPS, платёжный бой и контур 1С в программу не входят как цели атаки.
- Карта системы: `SECURITY_ARCHITECTURE_MAP.md`. Поверхность: `SECURITY_ATTACK_SURFACE.md`.
- Код приложения этой программой не исправляется.

Оценки критичности ниже — ожидаемый потолок, если проверка подтвердит сценарий. До подтверждения это не находки.

## 0. Правила, общие для каждой проверки

Подтверждение строится на синтетических записях, локальном Django test client или изолированной БД тестов. Реальные телефоны, заказы, платежи и дампы не выгружаются. Секреты в отчёте маскируются. Сканер без результата не считается доказательством отсутствия дефекта. Область, для которой нет VPS, тестового магазина ЮKassa, контура 1С или S3, получает статус **НЕ ПРОВЕРЕНО**.

Запрещено во всех проверках: атаки на чужие сайты и на боевую ЮKassa; реальные платежи и возвраты; изменяющие запросы в реальную 1С; изменение данных клиентов; DoS и массовый перебор паролей; выгрузка пользовательских таблиц; эксплуатация до получения настоящей БД; смена `.env`, production-настроек, volumes; `docker compose down -v`; `git reset --hard`, `git clean`, commit, push, deploy; отключение защитных механизмов.

Инструменты, которые допустимо запустить локально по коду, если они уже есть или ставятся из официального индекса: Bandit, Semgrep, pip-audit, npm audit, Gitleaks, Trivy, Checkov, `manage.py check --deploy`. Версия, команда, область, сырой итог без секретов и ложные срабатывания фиксируются в `SECURITY_FINDINGS.md` или приложении к финальному отчёту. Установка с непроверенных источников не выполняется.

## 1. Архитектура и границы доверия

### ARC-01. Полнота точек входа

1. Название: сверка маршрутов с картой.
2. Угроза: забытый endpoint без прав.
3. Использование: прямой запрос в обход интерфейса.
4. Компоненты: `config/urls.py`, `config/api_urls.py`, `apps/*/urls.py`, `frontend/src/proxy.ts`.
5. Способ: сравнить `path()` и `router.register` с поверхностью атаки; найти view без `permission_classes`.
6. Подтверждение: список расхождений файл:строка, без запросов к продакшену.
7. Ущерб: несанкционированное чтение или запись.
8. Критичность: High, если endpoint меняет заказ, роль или оплату; Medium, если только лишнее чтение.
9. Доказательства: таблица endpoint → класс прав → файл.
10. Запрещено: фаззинг продакшена.

### ARC-02. Доверие к заголовкам прокси

1. Название: `X-Forwarded-For` и `REMOTE_ADDR`.
2. Угроза: подделка IP для axes, throttle и allowlist ЮKassa.
3. Использование: заголовок с «доверенного» IP, обход блокировки и webhook-фильтра.
4. Компоненты: `production.py` `TRUST_PROXY`, `AXES_IPWARE_PROXY_COUNT`, `YooKassaWebhookView`, пример nginx.
5. Способ: прочитать, какой заголовок читает код; для webhook подтверждено чтение только `REMOTE_ADDR`. Проверить, не переписывает ли Django `REMOTE_ADDR` из клиентского заголовка без числа прокси.
6. Подтверждение: unit-тест или разбор `request.META` на локальном клиенте. Реальный nginx — НЕ ПРОВЕРЕНО, пока нет VPS.
7. Ущерб: обход блокировки входа или приём webhook не от ЮKassa (если re-fetch тоже обойдён — см. PAY).
8. Критичность: Medium сама по себе; High в цепочке с оплатой.
9. Доказательства: фрагмент кода и локальный запрос с поддельным заголовком, без секретов.
10. Запрещено: слать поддельные webhook на боевой хост.

### ARC-03. Смешение dev и prod

1. Название: слабые дефолты development не должны быть достижимы как production.
2. Угроза: запуск `docker-compose.yml` без overlay на VPS.
3. Использование: открытые 5432/6379 со слабым паролем.
4. Компоненты: `docker-compose.yml`, `docker-compose.prod.yml`, `settings/development.py`.
5. Способ: статически сравнить порты, пароли по умолчанию и `DEBUG`. Факт запуска на VPS — НЕ ПРОВЕРЕНО.
6. Подтверждение: цитаты compose. Не подключаться к чужому Postgres.
7. Ущерб: полная БД, если такой профиль опубликован.
8. Критичность: Critical при подтверждённой публикации; Informational как риск конфигурации, пока VPS не виден.
9. Доказательства: diff профилей и статус «не проверено на хосте».
10. Запрещено: сканирование внешнего IP и подбор пароля БД.

## 2. Контроль доступа и административная панель

### ACC-01. Django Admin без сессии

1. Название: анонимный доступ к Django Admin.
2. Угроза: чтение и правка моделей.
3. Использование: `GET/POST /{ADMIN_SITE_URL_PATH}`.
4. Компоненты: `config/urls.py`, `OTPAdminSite`.
5. Способ: Django test client без сессии на список моделей.
6. Подтверждение: ожидается редирект на логин. Фиксировать код ответа, не HTML с данными.
7. Ущерб: полная компрометация данных.
8. Критичность: Critical.
9. Доказательства: статус и заголовок `Location`, без учётных данных.
10. Запрещено: перебор пароля администратора.

### ACC-02. Витринная админка только на frontend

1. Название: обход `proxy.ts` прямым вызовом API.
2. Угроза: права «спрятаны кнопкой».
3. Использование: JWT покупателя на `/api/v1/admin/users/` и `/admin/onec/sync/apply/`.
4. Компоненты: `admin_api`, `permissions.py`, `proxy.ts`.
5. Способ: тест с пользователем `is_staff=False` и со staff без нужной группы.
6. Подтверждение: 401/403 на каждом методе, который меняет данные. Выборочно все группы, не один URL.
7. Ущерб: список клиентов, смена цен, apply каталога.
8. Критичность: Critical при обходе; проверка обязательна даже если UI закрыт.
9. Доказательства: метод, путь, код, отсутствие тела с PII.
10. Запрещено: использовать боевой токен сотрудника.

### ACC-03. Повышение привилегий

1. Название: смена собственной роли.
2. Угроза: mass assignment `is_staff`, `is_superuser`, `groups`.
3. Использование: `PATCH /auth/me/` или регистрация с лишними полями; staff группы users меняет себе группы.
4. Компоненты: сериализаторы users и `UserAdminUpdateView`.
5. Способ: передать лишние поля синтетическому пользователю.
6. Подтверждение: поля игнорируются или 403; в БД роль не изменилась. Откат тестового пользователя.
7. Ущерб: полный админ.
8. Критичность: Critical.
9. Доказательства: запрос без пароля, ответ, значение `is_staff` после.
10. Запрещено: повышать реального пользователя.

### ACC-04. IDOR заказов, адресов, возвратов

1. Название: доступ к чужому объекту по UUID/id.
2. Угроза: Broken Object Level Authorization.
3. Использование: подмена id в `GET/PATCH /orders/{id}/`, адресах, returns, pay, cancel, reorder.
4. Компоненты: orders, users, returns, payments views.
5. Способ: два синтетических пользователя и один гостевой заказ; запрос от чужого субъекта.
6. Подтверждение: 403/404 без полей телефона и адреса. Свой объект при этом читается.
7. Ущерб: PII и смена чужого заказа.
8. Критичность: High.
9. Доказательства: пара id «свой/чужой» и коды ответов. Значения PII не копировать.
10. Запрещено: перебирать реальные UUID продакшена.

### ACC-05. BFLA между группами

1. Название: сотрудник каталога вызывает заказы, пользователей, бэкап.
2. Угроза: горизонтальное повышение внутри staff.
3. Использование: валидный staff JWT группы A на endpoint группы B.
4. Компоненты: `HasAdminGroupPermission`, backup views, reports, users.
5. Способ: фикстуры групп `ringoo_*` без superuser.
6. Подтверждение: 403. Суперпользователь при этом допускается — это задумка, не дефект, если MFA включена.
7. Ущерб: экспорт заказов и скачивание бэкапа при слабой группе.
8. Критичность: High.
9. Доказательства: матрица группа × endpoint × код.
10. Запрещено: менять группы реальных сотрудников.

### ACC-06. MFA и блокировка

1. Название: staff API после блокировки и без TOTP.
2. Угроза: отозванный или заблокированный сотрудник сохраняет доступ; обход второго фактора.
3. Использование: старый JWT после `is_active=False`; JWT без claim `admin_mfa` при `ADMIN_OTP_ENABLED`.
4. Компоненты: `AdminMfaVerified`, SimpleJWT, axes не покрывает уже выданный JWT.
5. Способ: выдать токен, затем деактивировать пользователя; отдельно токен без MFA.
6. Подтверждение: 401/403. Если заблокированный пользователь ещё ходит до истечения access — это находка с критичностью не ниже High.
7. Ущерб: действия уволенного сотрудника до 30 минут или дольше, если проверяется только подпись.
8. Критичность: High.
9. Доказательства: код ответа до и после деактивации на синтетическом staff.
10. Запрещено: блокировать реальных людей.

### ACC-07. Повторное использование refresh

1. Название: ротация и blacklist.
2. Угроза: украденный refresh живёт после logout и после ротации.
3. Использование: повтор старого refresh.
4. Компоненты: `SIMPLE_JWT`, `token_blacklist`, `LogoutView`, `CookieTokenRefreshView`.
5. Способ: login синтетического пользователя, refresh, повтор того же refresh, logout, повтор.
6. Подтверждение: второй refresh и refresh после logout дают 401.
7. Ущерб: захват сессии.
8. Критичность: High при успешном повторе.
9. Доказательства: коды ответов; токены в отчёт не вставлять.
10. Запрещено: перехватывать чужие refresh.

## 3. Аутентификация

### AUTH-01. Учётные данные и перечисление

1. Название: регистрация, вход, смена пароля, сброс, смена телефона и email.
2. Угроза: захват аккаунта без пароля, перечисление существующих телефонов.
3. Использование: разные ответы «нет пользователя» / «письмо отправлено»; слабый токен сброса; смена email без подтверждения владения.
4. Компоненты: `apps/users/views.py`, `password_reset.py`, PhoneBackend, axes.
5. Способ: два синтетических номера; сравнить статус и форму тела, не время с точностью сети. Проверить одноразовость и срок токена сброса по коду и одному тесту.
6. Подтверждение: ответы неразличимы для существующего и несуществующего номера; токен сброса не подходит дважды.
7. Ущерб: захват почты и заказов жертвы.
8. Критичность: High при предсказуемом токене или различимом ответе, которым можно массово собирать телефоны; Medium при только временной утечке.
9. Доказательства: коды и урезанные тела без токена сброса.
10. Запрещено: массовый перебор и запросы к реальным номерам.

### AUTH-02. Хранение сессии на клиенте

1. Название: JWT в cookie и в localStorage.
2. Угроза: кража сессии через XSS.
3. Использование: чтение `localStorage` или не-HttpOnly cookie; токены в JSON, если нет `X-Auth-Cookies`.
4. Компоненты: `jwt_cookies.py`, `token-storage.ts`, `auth-mode.ts`, axios-интерцептор.
5. Способ: проследить, шлёт ли клиент заголовок всегда в production; убедиться, что access/refresh HttpOnly, а `ringoo_session` не содержит JWT.
6. Подтверждение: флаги `Set-Cookie` на локальном login синтетического пользователя. Значение cookie не логировать.
7. Ущерб: полный доступ в пределах жизни refresh (7 дней), если токен читается скриптом.
8. Критичность: High, если production-клиент хранит refresh в localStorage или отдаёт его в JSON при включённых cookie.
9. Доказательства: имена флагов, не значения.
10. Запрещено: внедрять XSS в работающий сайт.

### AUTH-03. CSRF, CORS, brute force

1. Название: куки-сессия против поддельного сайта и перебор пароля.
2. Угроза: чужой origin с `credentials`; неограниченный подбор.
3. Использование: браузер жертвы шлёт cookie на API; скрипт перебирает пароль.
4. Компоненты: CORS, CSRF middleware, `JwtCookieCsrfMiddleware`, axes, throttle `auth_login`.
5. Способ: тест CORS preflight с чужим Origin на локальном сервере; убедиться, что cookie-мутации требуют CSRF; лимит axes не проверять тысячами запросов — достаточно чтения настроек и одного локального порога на тестовом пользователе, если тест уже есть.
6. Подтверждение: чужой Origin не в `Access-Control-Allow-Origin` при credentials. Боевой хост — НЕ ПРОВЕРЕНО.
7. Ущерб: действия от имени жертвы или подбор пароля.
8. Критичность: High при `CORS *` с credentials или отсутствии CSRF на cookie-POST.
9. Доказательства: заголовки ответа.
10. Запрещено: перебор паролей на `test.ringoo15.store`.

## 4. Инъекции

### INJ-01. SQL и ORM

1. Название: влияние ввода на запрос.
2. Угроза: чтение или изменение БД.
3. Использование: поиск, сортировка, фильтры каталога, трекинг заказа, сырой SQL.
4. Компоненты: products views, orders, `cursor.execute`, `.raw(`, `.extra(`, `RawSQL`.
5. Способ: поиск конструкций с интерполяцией; там, где найдена, локальный запрос с маркером `' OR '1'='1` на тестовой БД. Уже видно: `health_check` выполняет константу `SELECT 1`; бэкап читает `SHOW server_version`.
6. Подтверждение: маркер не меняет число строк и не возвращает чужие таблицы. Ошибка БД не должна содержать весь SQL с данными.
7. Ущерб: компрометация БД.
8. Критичность: Critical при подтверждённой инъекции.
9. Доказательства: файл, строка, безопасный payload, код ответа. Дамп не снимать.
10. Запрещено: sqlmap против продакшена и извлечение реальных таблиц.

### INJ-02. Команды ОС, шаблоны, XML, путь

1. Название: command, SSTI, XXE, path traversal, log injection.
2. Угроза: выполнение команды или чтение файлов.
3. Использование: имя файла `../`, XML с сущностями из 1С, подстановка в `subprocess`.
4. Компоненты: `apps/backups/services.py` (`subprocess`), `integrations/onec/parser.py`, загрузки, шаблоны Django.
5. Способ: проследить, собирается ли команда из пользовательского ввода. Парсер XML открыть и проверить запрет внешних сущностей. Имена файлов — на `..` и абсолютные пути.
6. Подтверждение: тестовый XML с сущностью не приводит к чтению локального файла-маркера. Команда бэкапа не содержит полей запроса.
7. Ущерб: RCE или чтение секретов.
8. Критичность: Critical при достижимом RCE; High при чтении произвольного файла.
9. Доказательства: флаг парсера и результат на фикстуре. Содержимое `/etc/passwd` и ключей не приводить.
10. Запрещено: загружать исполняемые файлы в production и запускать restore в рабочую БД.

### INJ-03. XSS

1. Название: stored, reflected, DOM XSS.
2. Угроза: выполнение скрипта в браузере покупателя или сотрудника.
3. Использование: отзыв, название товара, новость, SEO-поле, `dangerouslySetInnerHTML`, URL `next`.
4. Компоненты: content serializers, admin формы, карточка товара, CSP.
5. Способ: поиск `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `document.write`. Для stored — маркер `<img src=x onerror=ringoo>` в синтетическом отзыве на тестовой БД и просмотр экранирования в React. Не оставлять маркер в общей БД.
6. Подтверждение: React экранирует текст; HTML-санитайзер есть там, где HTML задуман. CSP с `unsafe-inline` не считать самостоятельной уязвимостью, а усилителем.
7. Ущерб: кража сессии и действий сотрудника.
8. Критичность: High при stored XSS в админке или при чтении токена; Medium при само-XSS.
9. Доказательства: компонент и скрин/снимок DOM без чужих данных.
10. Запрещено: публиковать XSS на живом сайте.

## 5. Frontend

### FE-01. Секреты и лишние данные в клиенте

1. Название: `NEXT_PUBLIC_*`, source maps, внутренние URL.
2. Угроза: секрет, собранный в бандл, доступен любому посетителю.
3. Использование: чтение JS бандла.
4. Компоненты: `next.config.ts`, `frontend/src`, Dockerfile args.
5. Способ: поиск присваиваний секретов в `NEXT_PUBLIC_`; убедиться, что ключи ЮKassa, `SECRET_KEY`, пароль 1С не попадают в клиент. DSN Sentry и реквизиты организации — ожидаемо публичные, не дефект сами по себе.
6. Подтверждение: список имён переменных без значений.
7. Ущерб: компрометация платежного кабинета или БД, если секрет найден.
8. Критичность: Critical при секретном ключе в клиенте.
9. Доказательства: имя переменной и файл. Значение маскировать.
10. Запрещено: выводить `.env`.

### FE-02. Open redirect и SSRF серверных запросов

1. Название: параметр `next`, Server Actions, route handlers.
2. Угроза: увод на фишинговый сайт; сервер ходит на внутренний URL.
3. Использование: `?next=https://evil` после входа; server fetch по пользовательскому URL.
4. Компоненты: `proxy.ts`, страницы login, `frontend/src/app`.
5. Способ: найти потребление `next`; проверить, что разрешены только относительные пути этого сайта. Отдельных `route.ts` в `src/app` на момент карты нет; proxy rewrite идёт на фиксированный `RINGOO_API_PROXY_TARGET`.
6. Подтверждение: внешний URL не становится `Location`.
7. Ущерб: фишинг учётных данных.
8. Критичность: Medium.
9. Доказательства: код разбора и локальный переход.
10. Запрещено: редирект реальных пользователей.

### FE-03. Кэш и ошибки

1. Название: TanStack Query и сообщения об ошибках.
2. Угроза: чужие PII остаются в памяти вкладки; стек API показывается пользователю.
3. Использование: общий компьютер, смена аккаунта без очистки кэша.
4. Компоненты: query keys, logout, `getFriendlyErrorMessage`.

Каждая цепочка получает статус только после блоков 3–10. До этого в `SECURITY_ATTACK_SCENARIOS.md` пишется «не подтверждено».

### Сценарий A. Посетитель → админка

Старт: аноним. Шаги: публичный баг или массовое присвоение роли → staff API или Django Admin. Останов: серверные permissions, OTP, axes. Проверка: ACC-01…ACC-03, AUTH-01, INJ-03. Ущерб: полный контроль. Риск: по результату.

### Сценарий B. Пользователь → чужие данные

Старт: свой JWT. Шаги: чужой UUID. Останов: фильтр по `request.user`. Проверка: ACC-04. Ущерб: PII. Риск: по результату.

### Сценарий C. Frontend → закрытый API

Старт: бандл и storage. Шаги: секрет или токен → admin API. Останов: отсутствие секретов в клиенте и права на API. Проверка: FE-01, AUTH-02, ACC-02.

### Сценарий D. API → база

Старт: параметр поиска или заказа. Шаги: инъекция или чрезмерный serializer. Останов: ORM и параметризованный SQL. Проверка: INJ-01, API-01.

### Сценарий E. Оплата

Старт: свой неоплаченный заказ. Шаги: подмена статуса. Останов: re-fetch ЮKassa и сверка суммы. Проверка: PAY-01, PAY-02.

### Сценарий F. 1С

Старт: аноним или staff каталога. Шаги: apply или подмена ответа. Останов: группа, MFA, mock вместо живой 1С. Проверка: ONEC-01…03.

### Сценарий G. Бэкап

Старт: слабый staff или утёкший ключ. Шаги: download. Останов: отдельное право и шифрование. Проверка: BAK-01, ACC-05.

### Сценарий H. Инфраструктура

Старт: публичный сервис. Шаги: открытый порт Redis/Postgres или общая Docker-сеть. Останов: prod overlay и пароль. Проверка: ARC-03, DOCKER-02, NET-01. Пока нет VPS — цепочка не подтверждается.
