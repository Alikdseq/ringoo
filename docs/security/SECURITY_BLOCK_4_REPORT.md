# BLOCK 4. Backend и API

Дата: 2026-11-07. Код приложения не менялся. Рабочая база, ЮKassa, 1С, `test.ringoo15.store` и production-миграции не использовались.

Динамика: два прогона на `config.settings.test`. Движок `django.db.backends.sqlite3`, имя базы в памяти. Синтетические телефоны `+79990000001` … `+79990000012`. После прогона базы тестов разбираются.

## Что подтверждено статически

- Карта маршрутов из `config/urls.py`, `config/api_urls.py` и urls приложений. Бонусный публичный API и admin bonus не смонтированы.
- Admin API требует staff, группу и MFA-класс. Суперпользователь заменяет только проверку группы.
- Цена заказа перезаписывается в `OrderCreateSerializer.validate`. Статус заказа покупатель не шлёт. FSM админа не содержит оплаченного статуса.
- Оплата смотрит владельца или guest token и сумму заказа. `return_url` не берёт Host.
- `USE_X_FORWARDED_HOST` не включён. Сброс пароля и гостевое письмо берут `FRONTEND_URL`.
- Исходящие HTTP к 1С, ЮKassa, Сберу и Яндексу не принимают URL от покупателя.
- `ringoo_users` может менять `is_active` кому угодно. `is_staff` и группы — только суперпользователь.
- При `RETURNS_ENABLED` карточка возврата пускает любого staff. Флаг по умолчанию ложный, и тогда ответ 403 раньше этой строки.

## Что подтверждено динамически

Изолированная SQLite, аноним и два пользователя.

- `GET /api/v1/content/articles/?is_published=false` → 200, slug черновика.
- Карточка черновика → текст черновика и телефон автора.
- Карточка опубликованной статьи → тот же телефон автора.
- Обычный список статей → только опубликованная.
- `HTTP_HOST: evil.example` → 400 `DisallowedHost`.
- Пользователь A: `GET /orders/{заказ B}/` → 404, `GET /orders/` → пустой `results`.
- `PATCH /auth/me/` с `is_staff: true` и `is_superuser: true` → 200, в базе оба флага False.
- `GET /admin/orders/` без staff → 403.
- В ответе `/auth/me/` нет ключа `is_staff`.

## Вероятные, но не дожатые

- Гонка двух заказов по одному остатку. Код в транзакции, воспроизведения не было.
- Access JWT после logout остаётся годным до exp. Это поведение SimpleJWT. Отдельный запрос со старым access после blacklist refresh не делался.
- Токен пользователя с `is_active=False`. Опора на стандартный `get_user`, без своего прогона.

## Потенциальный риск, не уязвимость

- Номер заказа и телефон дают урезанный статус. Так написано в `guest_access.py`. Лимит 5/мин. Полный заказ так не отдаётся.
- Контакты магазина на публичной карточке точки — телефон и email магазина, не логин сотрудника.
- Если `ALLOWED_HOSTS` на VPS шире нужного, пагинация сможет сослаться на разрешённый лишний host. Список production не смотрелся.
- Базовый URL 1С без запрета частных сетей. Управляет настройка, не запрос покупателя.
- Импорт XLSX и скачивание бэкапа существуют и закрыты группой или суперпользователем. Файлы не гонялись.

## Не проверено

- Живой nginx, `X-Forwarded-*` на VPS, реальный `ALLOWED_HOSTS`.
- Вызов ЮKassa, webhook, сумма на стороне кассы. Блок 8.
- Apply 1С. Блок 9.
- Django Admin: вход, TOTP, экспорт, inline. Блок 5.
- Попарные HTTP-запросы всех групп `ringoo_*`.
- Гонки остатков, повторный pay уже оплаченного заказа живым запросом.
- Нагрузка и обход throttle сменой IP.
- Содержимое трассировки 500 на production.

## Ложные следы

- Публичный `AllowAny` на `POST /orders/` и `POST /orders/{id}/pay/` выглядит как отсутствие прав. Дальше владелец и сумма проверяются в коде. Это не открытая оплата чужого заказа.
- `author_phone` легко принять за контакт редакции. Поле читает `CustomUser.phone`, а это логин. Находка остаётся.
- Отсутствие кнопки в интерфейсе не использовалось как довод. Маршруты взяты из urls.

## Ответы

1. Может ли аноним получить закрытые данные через API? **YES.** Черновики статей и новостей и телефон автора. Заказы, профили и admin API — нет.
2. Может ли обычный пользователь получить чужой заказ? **NO.** Карточка 404, список пустой. Урезанный статус по телефону и номеру — отдельный задуманный ответ, не карточка заказа.
3. Может ли обычный пользователь изменить чужой заказ? **NO.** Правки заказа у покупателя нет. Отмена и оплата проверяют владельца или guest token.
4. Может ли пользователь изменить собственную роль? **NO.** SQLite: `is_staff` в PATCH профиля не записался.
5. Может ли сотрудник получить административные права? **NO.** `is_staff` и группы ставит только суперпользователь. Сотрудник не назначает себе новую группу. Отдельный дефект AUTH-001: группа пользователей может снова включить уже существующего staff.
6. Может ли сотрудник изменить каталог без своих полномочий? **NO.** Запись требует `ringoo_catalog`. Чужая группа по коду не проходит. HTTP каждой группы не гонялся, механизм класса один.
7. Может ли пользователь создать заказ по произвольной цене? **NO.** `validate` подставляет цену каталога и заново считает итог. Сам POST на SQLite не вызывался.
8. Может ли пользователь изменить итоговую сумму заказа? **NO.** Поля суммы в клиентском PATCH нет. Итог при создании затирается.
9. Может ли пользователь оплатить чужой заказ? **NO.** `_can_access_order` не пускает чужого и не даёт staff-bypass. Запрос в ЮKassa не отправлялся.
10. Может ли пользователь получить чужой payment URL? **NO.** Тот же шлюз, до обращения к кассе.
11. Может ли пользователь изменить статус заказа на paid? **NO.** Такого поля у покупателя нет. Админский FSM в paid не ведёт. Успех оплаты решает сверка с кассой, это блок 8.
12. Может ли произвольный Host попасть в абсолютные URL API? **PARTIAL.** Чужой host вне списка получил 400. Разрешённый лишний host и nginx production не проверялись.
13. Может ли произвольный Host повлиять на confirmation_url? **NO.** Возврат берётся из `YOOKASSA_RETURN_URL` или `FRONTEND_URL`. `form_url` приходит от ЮKassa.
14. Есть ли SSRF? **NO.** URL запроса покупателя в исходящий HTTP не подставляется.
15. Есть ли утечки персональных данных? **YES.** Телефон автора (API-001). Чужие заказы и профили публичным API не отдаются.
16. Есть ли административные endpoints без надлежащей защиты? **NO** для `/api/v1/admin/`: без staff 403. Django Admin в этом прогоне не открывался. Черновики контента — не admin endpoint, они закрыты плохо (API-002).
17. Есть ли возможность выполнить привилегированное действие через фоновые задачи? **NO** для анонима и покупателя. Apply 1С и бэкап требуют каталог или суперпользователя. Очередь Redis снаружи — блок 6.
18. Есть ли цепочка от FE-002 до административных действий? **PARTIAL.** Бэкенд сам права не выдаёт. Записать строку в каталог может `ringoo_catalog` или 1С. Дальше скрипт на витрине выполняется в браузере того, кто открыл страницу, и может звать API его cookie. Аноним этот текст в каталог не кладёт.

## Что чинить первым после полного аудита

Не в этом проходе.

1. Убрать `author_phone` из публичных сериализаторов и перестать принимать `is_published` на публичном списке. Это единственные подтверждённые дыры, которые открыты без staff.
2. FE-002: экранирование JSON-LD. Иначе запись каталожной группы становится скриптом на витрине.
3. До включения возвратов убрать `is_staff` с клиентских return-view.
4. Ограничить `is_active` так, чтобы группа пользователей не выключала суперпользователя и не включала staff обратно.
