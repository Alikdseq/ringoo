# BLOCK 5. Django Admin, TOTP, отзыв токена и группы

Дата: 2026-11-07. Код приложения не менялся. Рабочая база, ЮKassa, 1С, публичный домен и VPS не использовались.

## Конфигурация

`DJANGO_SETTINGS_MODULE=config.settings.test`. Движок `django.db.backends.sqlite3`, имя `file:memorydb_default?mode=memory&cache=shared`. Перед запросами скрипт проверял движок. Пользователи создавались только в этой базе и удалялись вместе с ней. Пароли в отчёт не переносятся.

Два прогона.

1. Флаг OTP как в test settings: `False`. Класс площадки Django Admin — обычный. Матрица групп, AUTH-001, access после `is_active=False`, Django Admin без TOTP.
2. В том же виде процесса, до первого запроса, `ADMIN_OTP_ENABLED` выставлен в True и в middleware добавлен `OTPMiddleware`. Файл settings на диске не редактировался. Форма входа Django Admin содержала поле `otp_token`. Пароль без кода не пускал. Это поведение `OTPAdminSite`.

`django_otp.plugins.otp_static` в приложениях нет. Recovery-кодов TOTP в проекте нет.

## Файлы

- `backend/config/urls.py` — `admin.site.urls` на `ADMIN_SITE_URL_PATH`. При включённом флаге на момент импорта urls класс площадки становится `OTPAdminSite`.
- `backend/config/settings/base.py` — путь из `DJANGO_ADMIN_URL`, иначе `admin/`. В этом прогоне путь был `admin/`. Значение на сервере не читалось.
- `backend/apps/users/admin_mfa.py` — секрет в `TOTPDevice`, проверка `verify_token`, claim `admin_mfa`.
- `backend/apps/users/views.py` — `/auth/mfa/verify/`, refresh без проверки `is_active`.
- `backend/apps/admin_api/permissions.py` — восемь групп: `ringoo_orders`, `ringoo_catalog`, `ringoo_content`, `ringoo_crm`, `ringoo_reports`, `ringoo_users`, `ringoo_stores`, `ringoo_bonus`.
- ModelAdmin: заказы, платежи, пользователи, каталог, контент, CRM, аудит, корзина, бонусы, возвраты, акции, магазины. Свои `has_*_permission` есть у согласия (запрет записи), журнала аудита (запрет записи), лога 1С (запрет записи) и счёта бонусов (запрет создания). Остальные сидят на стандартных правах Django `is_staff` плюс permission модели. Группы `ringoo_*` Django Admin не читает.

Маршруты `/admin/` и `/api/v1/admin/` разные. Первый — сессия Django. Второй — JWT. Витрина Next тоже зовётся `/admin`, это другой процесс. Скрытие пути админки защитой не считается: проверялись и индекс, и URL модели.

## Access и refresh после `is_active=False`

Синтетический пользователь. Токены выпущены до блокировки.

| Запрос | До | После `is_active=False` |
|---|---|---|
| `GET /api/v1/auth/me/` | 200 | 401 `user_inactive` |
| `GET /api/v1/orders/` | 200 | 401 `user_inactive` |
| `GET /api/v1/admin/orders/` | — | 401 `user_inactive` |
| `GET /api/v1/products/products/` с тем же Bearer | — | 401. Публичный каталог с этим заголовком не превращается в гостя: `AuthenticationFailed` lenient-класс не глотает |
| `POST /api/v1/auth/token/` паролем | — | 401 |
| `POST /api/v1/auth/token/refresh/` | — | 200, в ответе новый access |
| `GET /auth/me/` этим новым access | — | 401 `user_inactive` |

Access на каждом запросе проверяет живого пользователя. Называть его отозванным через blacklist нельзя: blacklist access нет. Для чтения данных он мёртв.

Refresh на блокировке в blacklist не пишется. Endpoint его принимает и выпускает новую пару. Новая пара данные не открывает. Это RINGOO-AUTH-002, INFO.

Отдельный staff каталога, созданный уже неактивным: заранее собранный access на товары — 401, пароль — 401.

## Остаточные риски

Django Admin пускает любого `is_staff`, а дальше режет правами моделей Django, не группами витрины. Новый сотрудник каталога модели не видит. Если ему отдельно выдать `change_order` или сделать суперпользователем, группы `ringoo_*` его не остановят. В форме пользователя Django Admin есть `is_staff` и `is_superuser`. Менять их может тот, у кого есть право менять пользователя. У каталога этого права нет: POST на список пользователей — 403.

Пока OTP выключен, пароль staff открывает индекс Django Admin. В production-модуле OTP обязателен. Этот прогон включал OTP отдельно и видел отказ без кода.

## Что делать, код здесь не менялся

1. Оставить ограничение `is_active` из AUTH-001: группа пользователей не включает суперпользователя и не возвращает staff.
2. Дашборд с суммами отдать группе отчётов.
3. На refresh проверять `is_active` и не выпускать пару.
4. Не выдавать сотрудникам витрины права моделей Django и не делать их суперпользователями без нужды. Группы `ringoo_*` Django Admin не заменяют.
