# BLOCK 6. Инфраструктура, Docker, прокси, копии

Дата: 2026-11-07. Код, Compose, Nginx, `.env` и сервер не менялись. Контейнеры не перезапускались. К VPS и публичному домену запросов не было. ЮKassa и 1С не вызывались. Резервная копия не снималась и не разворачивалась.

Проверка — чтение файлов. Статус «есть в репозитории» не равен «так работает на сервере».

## 1. Подтверждено в репозитории

- Шесть сервисов: db, redis, web, frontend, celery, celery-beat. Образы Postgres 15 и Redis 7 зафиксированы тегами, не `latest`.
- Production Dockerfile: multi-stage, пользователь `django` и `nextjs`. Dev Dockerfile пользователя не задаёт (процесс root).
- В compose нет privileged, лишних capabilities, host-сети и сокета Docker.
- Prod overlay убирает публикацию портов базы и Redis и сажает 3000/8000 на `127.0.0.1`. Требует сильные `SECRET_KEY`, `DATABASE_URL`, `REDIS_URL`.
- Модуль `config.settings.production` не стартует с DEBUG, слабым ключом, суперпользователем БД, пустым Redis-паролем и CORS `*`.
- `USE_X_FORWARDED_HOST` не включён. `X-Forwarded-Proto` принимается только при `TRUST_PROXY`.
- S3-адаптер резервных копий по умолчанию выключен, при включении пишет `ACL=private` и сверяет размер. SHA256 есть в коде verify.
- `.dockerignore` не копирует `.env` и `.git` в контекст образа.

## 4. Внешние сервисы

S3, ЮKassa, 1С, SMTP, Sentry и внешний uptime в этом блоке не вызывались. Код Sentry и мониторинга описывает, куда смотреть. Работающих оповещений в репозитории нет.

## 5. Restore drill

Не выполнялся и на рабочую базу не планировался. Сценарий на потом: пустой контейнер Postgres, копия синтетического дампа, сверка SHA256, подъём, отказ от `--drop` на любой базе с живыми заказами.

## Ответы

1. Какие контейнеры от root? **PARTIAL.** Dev-образы web, frontend, celery и beat `USER` не задают. Production Dockerfile задаёт `django` и `nextjs`. Запущенные контейнеры не смотрелись. Postgres и Redis в compose пользователя не переопределяют.
2. Есть ли опубликованные внутренние порты? **YES** в `docker-compose.yml`: 5436→5432 и 6380→6379. **NO** в prod overlay, если он реально подмешан. На сервере **NOT TESTED**.
3. Может ли внешний пользователь открыть Postgres или Redis? **NOT TESTED** на VPS. По prod overlay порты не публикуются. По базовому файлу — да, если этот файл поднят на хосте с белым IP.
4. Опасные capabilities или mounts? **NO** в прочитанных compose. Bind `./backend:/app` есть только в базовом файле. Сокета Docker нет.
5. Проверена ли production Nginx-конфигурация? **NO.** Прочитан пример в репозитории.
6. Есть ли корректный HTTP → HTTPS redirect? **NOT TESTED.** В примере Nginx блока `listen 80` нет.
7. Подтверждён ли TLS на домене? **NOT TESTED.**
8. Включены ли production Django security settings? **YES** в модуле `production.py`, если процесс стартовал с ним: DEBUG запрещён, HSTS, secure cookie, DENY, nosniff, OTP обязателен. Что загружено на сервере — **NOT TESTED**.
9. Есть ли секреты в репозитории или образах? **PARTIAL.** Боевые значения не печатались. В gitignore секреты исключены, в Dockerfile они не зашиты, `.dockerignore` отсекает `.env`. В базовом compose есть слабый fallback пароля базы. Образы не распаковывались.
10. Защищены ли PostgreSQL и Redis? **PARTIAL.** Prod settings не пускают слабую роль и пустой пароль Redis. Базовый compose публикует оба сервиса и допускает пустой пароль Redis. Сеть сервера не проверялась.
11. Безопасно ли запускаются Celery и Beat? **PARTIAL.** В prod тот же непривилегированный образ, без порта наружу, JSON-задачи, restart unless-stopped. Healthcheck нет. Какие задачи сейчас в расписании на сервере, зависит от флагов env. Не запускались.
12. Что попадает в резервную копию? **База и media** (`backup-set.sh` и Django zip). `.env` в архив по задумке не входит. Факт последней копии не смотрелся.
13. Подключён ли реальный S3? **NOT TESTED.** Код есть, флаг по умолчанию выключен.
14. Загружаются ли архивы с проверкой целостности? **PARTIAL.** В коде есть SHA256, `gzip -t` и сверка размера после `put_object`. Успешной загрузки в этом блоке не было.
15. Есть ли подтверждённый restore drill? **NO.**
16. Защищены ли архивы от публичного доступа? **PARTIAL.** Скачивание в API — суперпользователь. S3 ACL в коде `private`. Политика бакета и права каталога `backups/` на диске сервера не смотрелись.
17. Есть ли мониторинг и уведомления? **PARTIAL.** Есть `/health/`, документ и команда `report_ops_alerts`. Работающего внешнего мониторинга и писем при падении backup в этом блоке не видно.
18. Определены ли RPO и RTO? **NO.** В документации это рекомендация ≤ 24 ч / ≤ 4 ч и прямо сказано, что владелец их не утвердил. Время восстановления не измерялось.
19. Что будет при перезагрузке VPS? **PARTIAL.** Prod overlay просит Docker поднять контейнеры (`unless-stopped`). Тома Postgres и Redis AOF при этом не описаны как стираемые. Сработает ли это, не проверялось. Пропущенные тики beat сами не догоняются. Оповещения нет.
20. Что чинить до запуска, без вердикта о всём магазине? Не поднимать базовый compose на белом IP. Не пользоваться overlay с `ports: []`. Снять живой Nginx/Caddy и TLS отдельным разрешённым заходом. Включить шифрование backup и убедиться, что cron есть. Не запускать `restore-db.sh --drop` на рабочей базе. Провести drill на пустой базе. Пока этого нет, наличие скриптов не означает, что магазин восстанавливается.
