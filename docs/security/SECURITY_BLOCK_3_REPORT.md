- Дата: 2026-11-07
- Объект: `frontend/` (Next.js 16.4.3, React 19).

## 1. Открытый редирект (FE-001)

Исследованы `next`, `returnUrl`, `redirect`, `callbackUrl`, `router.push`, `router.replace`, `window.location`, `location.assign`, `location.href`.

Приёмники непроверенного `next` — только три: вход, регистрация, вход сотрудника. После успеха все три вызывают `router.push(next)`.

Изолированный разбор URL (тот же конструктор, что у Next):

| Значение | Чужой origin |
|---|---|
| `/profile`, `/orders/1` | нет |
| `https://example.invalid/phish` | да |
| `//example.invalid/phish` | да |
| `///example.invalid`, `/\\example.invalid`, `\\example.invalid` | да |
| `javascript:alert(1)` | разобрался как `javascript:`, но Next до перехода бросает ошибку и не вызывает `location.assign` |

Фишинг возможен. Обхода авторизации, MFA, cookie и прав нет: переход случается уже после успешного входа, а чужой сайт cookie магазина не получает. Критичность остаётся MEDIUM.

Сброс пароля ведёт только на `/login`. Страницы витрины, которые формируют `next`, подставляют свой путь. Платёжные `location.assign` доверяют URL из API — см. передачу в блок 8, это не FE-001.

Статус проверки: FAIL для трёх страниц входа. PASS по коду для сброса пароля и для мест, которые лишь записывают внутренний путь.

## 2. JSON-LD и XSS (FE-002)

Единственные `dangerouslySetInnerHTML` в `src`: JSON-LD и константный скрипт темы.

Поля в JSON-LD: название, бренд, sku, meta и краткое описание, описание (только запасной вариант и с вырезанием тегов), крошки, имя и описание магазина, адрес. Пишут их экраны админки каталога и магазинов; серверная роль подтверждается в блоке 5. Синхронизация 1С пишет те же поля товара.

`JSON.stringify` не экранирует `<`. CSP на всех страницах из `next.config.ts` содержит `'unsafe-inline'`, поэтому встроенный скрипт после разрыва тега не блокируется. Другого фильтра на этом пути нет.

Изолированный прогон jsdom:

- сырой `JSON.stringify` строки `</script><script>window.__hit=1</script>` дал два тега script, флаг стал 1;
- замена `<` на `\u003c` оставила один `application/ld+json`, флаг остался 0.

Текст карточки через `stripDescriptionHtml` попадает в текстовый узел React и этот канал не ломает. Новости и блог HTML из API не выводят.

Последствия при открытии страницы жертвой: запросы с её cookie, чтение CSRF-cookie и `sessionStorage` (гостевой токен). HttpOnly access/refresh из JS не читаются, пока не включён режим `localStorage`. Сотрудник и покупатель делят origin, поэтому сценарий «автор карточки действует сессией того, кто её открыл» реален. Критичность изменена с MEDIUM на HIGH. Не CRITICAL: нет анонимной записи и нет чтения HttpOnly JWT.

Статус: FAIL, динамика в jsdom, не в витрине.

## 3. `NEXT_PUBLIC_*` и прочая конфигурация клиента

В браузерный бандл Next вшивает только `NEXT_PUBLIC_*`. Остальные env из таблицы ниже в клиентский код не попадают, если их не прокинули под этим префиксом.

| Имя | Где | В бандле | Секрет? | Если увидят |
|---|---|---|---|---|
| `NEXT_PUBLIC_API_V1_URL`, `NEXT_PUBLIC_API_URL` | клиент API, CSP, картинки | да | нет, это адрес API | знают, куда слать запросы; адрес и так виден в сети |
| `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_APP_URL` | SEO, CSP | да | нет | канонический origin |
| `NEXT_PUBLIC_USE_AUTH_COOKIES` | режим сессии | да | нет | видно, лежат ли JWT в `localStorage` |
| `NEXT_PUBLIC_JWT_COOKIE_ACCESS_NAME`, `NEXT_PUBLIC_JWT_COOKIE_REFRESH_NAME` | `proxy.ts` | имена да | нет | имена cookie, не значения |
| `NEXT_PUBLIC_ONLINE_PAYMENT_ENABLED`, `NEXT_PUBLIC_RETURNS_ENABLED`, `NEXT_PUBLIC_PROMOCODES_ENABLED`, `NEXT_PUBLIC_LOYALTY_UI_ENABLED`, `NEXT_PUBLIC_DATA_EXPORT_UI_ENABLED`, `NEXT_PUBLIC_XLSX_IMPORT_ENABLED`, `NEXT_PUBLIC_BACKUP_NAV_ENABLED` | флаги UI | да | нет | какие кнопки собраны; сервер флаги обязан повторять |
| `NEXT_PUBLIC_POLICY_VERSION`, `NEXT_PUBLIC_ORG_*`, `NEXT_PUBLIC_PRIVACY_EMAIL` | реквизиты | да | нет, это публичные реквизиты | уже на сайте |
| `NEXT_PUBLIC_YANDEX_MAPS_API_KEY`, `NEXT_PUBLIC_YANDEX_SUGGEST_API_KEY` | карты | да | ключ браузерного API | расход квоты, не доступ к БД |
| `NEXT_PUBLIC_YANDEX_METRICA_ID` | счётчик | да | нет | id счётчика |
| `NEXT_PUBLIC_SENTRY_DSN` | Sentry | да | DSN публичен по устройству Sentry | шум в проекте ошибок |
| `NEXT_PUBLIC_MOBILE_FLAT_SECTIONS`, `NEXT_PUBLIC_DISABLE_LINK_PREFETCH`, `NEXT_PUBLIC_RINGOO_NGROK_DEMO` | UI | да | нет | нет |
| `API_INTERNAL_V1_URL`, `RINGOO_API_PROXY_TARGET` | только сервер Next | нет | внутренний URL | не должен попасть в бандл; в коде читается при `window === undefined` или в `proxy.ts` |
| `YOOKASSA_*`, `SECRET_KEY`, `ONE_C_*`, пароли БД | во фронтенде не читаются | нет | — | в этом дереве не найдены |

Dockerfile фронтенда передаёт в сборку URL, флаги оплаты и возвратов и имена cookie. Секрета шлюза там нет.

Отдельный production-бандл в этом блоке заново не собирался: это сетевая сборка и риск задеть окружение. Вывод сделан по исходникам и по уже лежащему `.next/static` (карт и явных секретов в рамках поиска имён нет). Статус: PASS по отсутствию серверных секретов в `NEXT_PUBLIC_*`. Ограничение: содержимое чужого `.env` на VPS не смотрелось.

## 4. Source maps

`next.config.ts` не включает `productionBrowserSourceMaps`. Sentry: `sourcemaps.disable: true`. В `.next/static` файлов `*.map` нет (0). В `.next/server` их 452 — это артефакт локальной сборки для серверных чанков, Next их по HTTP как статику не отдаёт. Каталога `.next/standalone` нет, Docker-образ в этом блоке не вскрывался. Комментарии и имена функций в серверных картах на диске разработчика есть; это раскрытие исходников тому, у кого диск, не посетителю сайта. Критичностью не считается.

Статус публичной отдачи: PASS. Статус «карт нет вообще на машине сборки»: не PASS, они есть в `.next/server`.

## 5. React Query

`QueryProvider` создаёт один клиент на модуль: `staleTime` 30 с, `refetchOnWindowFocus: true`, `retry: 1`. `gcTime` не задан (у библиотеки 5 минут). Persist в `localStorage` нет.

Выход удаляет признак staff и затирает `/auth/me`. Заказы, адреса, избранное, карточка заказа и админские списки остаются. Ключи без id пользователя. Адреса на checkout свежие 5 минут и совпадают по ключу с профилем.

Удалённо чужой кэш не прочитать. В той же вкладке, без F5, второй вход показывает чужие адреса и заказы, пока кэш свежий. Двумя аккаунтами это не прогонялось. Статус: FAIL, RINGOO-FE-003, MEDIUM.

## Итог блока

Проверенные области: страницы входа и регистрации, сброс пароля, витринные редиректы, оплатные переходы (только клиент), JSON-LD и текстовые описания, метаданные, заглушки новостей и блога, CSP, переменные `NEXT_PUBLIC_*`, source maps локальной сборки, React Query и logout, CSRF-заголовок клиента, proxy, sitemap, хранилище браузера, обработка ошибок, отсутствие Server Actions.

Найдено три проблемы.

Подтверждены:

- RINGOO-FE-001 MEDIUM. Изолированный разбор URL и код Next.js. Браузер магазина нет.
- RINGOO-FE-002 HIGH. jsdom показал выполнение скрипта. Каталог не менялся.
- RINGOO-FE-003 MEDIUM. Код и контракт кэша. Два аккаунта не входили.

Только статически, без изолированного прогона: FE-003. FE-001 и FE-002 получили дополнительное подтверждение вне витрины.

Не проверено:

- живой клик по `/login?next=https://example.invalid/`;
- карточка товара с маркером в настоящей или тестовой БД;
- смена пользователя в одной вкладке на запущенном Next;
- заголовки Referrer и CSP на развёрнутом хосте;
- содержимое production-образа Docker (standalone maps);
- referrer-restriction ключа Яндекса;
- что API оплаты не отдаёт чужой `form_url`.

Готовность фронтенда. Как набор экранов он не готов к выкладке, пока открыты FE-001 и FE-002: оба чинятся локально и не требуют VPS. FE-003 нужен до staging, если одним браузером пользуются несколько человек (касса, семья, общий компьютер). Эта оценка не про backend, оплату и 1С.

Критичность FE-001 не менялась: эффект — фишинг после настоящего входа, не кража сессии. FE-002 поднята до HIGH, потому что скрипт на origin магазина обходит смысл HttpOnly для действий от имени жертвы и не останавливается текущим CSP.

## Передача в блок 4 (backend и API)

Фронтенд уже показал три места, где сервер обязан не верить клиенту. Блок 4 начинает с них, не переписывая UI.

1. Матрица каждого маршрута: метод, аутентификация, permission, владелец объекта, лишние поля ответа. Особый приоритет: `POST /orders/`, цена и количество; `GET/PATCH /orders/{id}`; адреса; `POST /orders/{id}/pay` и кто имеет право получить `form_url`.
2. FE-NOTE-04: откуда берётся `confirmation_url` и может ли в него попасть host не ЮKassa и не Сбера.
3. Кто на сервере может записать `title`, `short_description`, `brand`, поля магазина (группа, 1С). Фронтенд лишь рисует формы.
4. Не считать спрятанные кнопки админки защитой. `proxy.ts` проверяет наличие cookie, не роль.
5. Ответы `detail` на логине: нет ли в них различия «пользователь не найден» и нет ли внутренних текстов. Это стык с блоком 5, но сериализаторы смотреть в блоке 4.
6. Пагинация `next` в sitemap доверяет абсолютному URL из API. Убедиться, что DRF не собирает `next` из заголовка Host, который прислал клиент.
