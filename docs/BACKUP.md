# Резервное копирование и восстановление

Политика резервного копирования Ringoo: ежедневные бэкапы БД и медиафайлов, проверенная схема восстановления в течение часа.

## Что бэкапится

| Объект | Частота | Скрипт | Результат |
|--------|---------|--------|----------|
| **База данных PostgreSQL** | Ежедневно (автоматически по cron) | `scripts/backup-db.sh` | `ringoo_db_YYYYMMDD_HHMMSS.sql.gz` |
| **Медиафайлы** (изображения, 3D-модели) | Ежедневно | `scripts/backup-media.sh` | `ringoo_media_YYYYMMDD_HHMMSS.tar.gz` |

Бэкапы сохраняются в каталог `backups/` в корне проекта (или в каталог, переданный аргументом). Рекомендуется хранить копии на отдельном диске или в облаке (S3, другой сервер).

## Ежедневное автоматическое копирование

### Linux / macOS (cron)

Добавьте в crontab (`crontab -e`) задачу на ежедневный запуск в 03:00:

```cron
0 3 * * * cd /path/to/ringoo && make backup
```

Или напрямую скрипт с указанием каталога и срока хранения (в днях):

```cron
0 3 * * * BACKUP_KEEP_DAYS=7 /path/to/ringoo/scripts/backup-all.sh /path/to/ringoo/backups
```

По умолчанию хранятся бэкапы за последние **7 дней** (`BACKUP_KEEP_DAYS=7`). Старые файлы удаляются при каждом запуске `backup-all.sh`.

### Windows

- **Вариант 1:** Запуск через WSL или Git Bash: добавить в Планировщик заданий Windows задачу, которая вызывает `bash scripts/backup-all.sh` (путь к проекту и bash указать явно).
- **Вариант 2:** Запуск внутри контейнера по расписанию: отдельный сервис в docker-compose с cron, который раз в сутки выполняет `backup-db.sh` и копирует медиа (образ с `pg_dump`, `gzip`, `tar`).

### Имена Docker-ресурсов

Скрипты ожидают контейнер БД `ringoo_db` и volume медиа `ringoo_media_volume` (имя формируется как `<проект>_<volume из compose>`). Если имена другие, задайте переменные:

```bash
export DB_CONTAINER=my_db_container
export MEDIA_VOLUME=my_project_media_volume
./scripts/backup-all.sh
```

## Ручной запуск бэкапа

```bash
# Полный бэкап (БД + медиа), каталог по умолчанию ./backups
make backup

# Только БД
make backup-db

# Только медиа
make backup-media

# Указать свой каталог
./scripts/backup-all.sh /var/backups/ringoo
```

## Восстановление из бэкапа (схема «подняться за час»)

Цель: восстановить работу из последнего бэкапа в течение **не более часа**. Ниже — пошаговая схема.

### Предусловия

- Установлены Docker и Docker Compose.
- Есть хотя бы один актуальный бэкап БД (`ringoo_db_*.sql.gz`) и при необходимости медиа (`ringoo_media_*.tar.gz`).

### Шаг 1. Остановить приложение (1–2 мин)

```bash
docker-compose down
# Или остановить только web/celery, оставив db для восстановления
docker-compose stop web celery celery-beat
```

### Шаг 2. Восстановить БД (5–15 мин в зависимости от размера)

Вариант **A**: восстановление в существующий контейнер и volume БД.

```bash
# Полная замена БД дампом (--drop удаляет текущие таблицы)
make restore-db DUMP=backups/ringoo_db_20260310_030000.sql.gz

# Или напрямую
./scripts/restore-db.sh backups/ringoo_db_20260310_030000.sql.gz --drop
```

Вариант **B**: чистая БД (например, после `docker-compose down -v` и нового поднятия `db`).

```bash
docker-compose up -d db
# Дождаться healthcheck (несколько секунд)
make migrate
make restore-db DUMP=backups/ringoo_db_20260310_030000.sql.gz
# Без --drop при пустой БД можно: ./scripts/restore-db.sh backups/ringoo_db_20260310_030000.sql.gz
```

После восстановления дампа при изменении схемы в коде выполнить:

```bash
make migrate
```

### Шаг 3. Восстановить медиа (5–20 мин в зависимости от объёма)

Если бэкап медиа делался, восстановить его в volume:

```bash
make restore-media ARCHIVE=backups/ringoo_media_20260310_030000.tar.gz

# Или напрямую
./scripts/restore-media.sh backups/ringoo_media_20260310_030000.tar.gz
```

Если volume создаётся заново, перед восстановлением поднять сервис `web` один раз (чтобы volume создался), затем выполнить команду выше.

### Шаг 4. Запустить сервисы и проверить (5–10 мин)

```bash
docker-compose up -d
make health
# Проверить в браузере: логин, каталог, картинки товаров
```

### Ориентировочное время

| Этап | Время |
|------|--------|
| Остановка сервисов | 1–2 мин |
| Восстановление БД | 5–15 мин |
| Восстановление медиа | 5–20 мин |
| Запуск и проверка | 5–10 мин |
| **Итого** | **до 1 часа** |

Для очень больших БД или объёмов медиа время может увеличиться; хранение бэкапов на быстром диске/сети уменьшает время восстановления.

## Проверка схемы восстановления

Рекомендуется раз в квартал проводить учебное восстановление:

1. Развернуть копию окружения (отдельный compose или тестовый сервер).
2. Восстановить последний бэкап БД и медиа по шагам выше.
3. Убедиться, что сайт открывается, логин работает, каталог и картинки отображаются.
4. Зафиксировать фактическое время и при необходимости обновить процедуру и документацию.

## Бэкапы вне Docker

- **БД:** при работе с внешним PostgreSQL запускайте `pg_dump` на стороне сервера БД (или с хоста с доступом к порту БД), результат сжимайте и сохраняйте по тому же расписанию.
- **Медиа:** при хранении файлов не в volume (например, на NFS или S3) настройте копирование/синхронизацию этих каталогов или бэкап S3 в соответствии с вашей политикой хранения.

## Резюме

- **БД** сохраняется ежедневно (автоматически по cron через `make backup` или `scripts/backup-all.sh`).
- **Файлы (изображения, 3D-модели)** бэкапятся тем же ежедневным запуском.
- **Схема восстановления** проверена: из бэкапа можно подняться за ориентировочный **час**, следуя шагам в этом документе.
