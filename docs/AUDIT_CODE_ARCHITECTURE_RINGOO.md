**Источники требований:** `ТЗ.txt`, `ARCHITECTURE.md`, `PLAN.md`, `docs/ARCHITECTURE.md`  
**Метод:** статический обзор кода и конфигурации без внесения изменений в продуктовый код  

**Примечание (актуализация):** бонусная программа в продукте временно скрыта (публичный и админский REST по бонусам отключены в URLconf; на фронтенде разделы убраны). Ниже аудит **не** содержит отдельных рекомендаций по исправлению бонусной логики до момента её повторного включения. **SMS-авторизация и SMS-интеграция удалены из кодовой базы** (вход — телефон/логин и пароль + JWT, как в текущем API).

## 1. Общая оценка

Проект демонстрирует **продуманную модульную структуру** Django-приложений, осмысленное использование DRF, кэширования списков каталога, атомарного резерва остатков для **самовывоза**, идемпотентности создания заказа, разделения публичного API и `admin_api` с проверкой `is_staff`, а также цельный слой клиента на фронтенде (axios + interceptors + TanStack Query).

Выявлены **критические разрывы между документацией/ТЗ и реализацией**, а также **ошибки уровня бизнес-логики и продакшен-образа**, которые при прямом выводе в эксплуатацию дадут финансовые потери или неработающий деплой. Отдельно стоит усилить безопасность хранения JWT и жёсткость CI (сейчас часть проверок фактически опциональна).

**Главные риски в одном абзаце:** доверие к ценам товаров и сумме заказа со стороны клиента при создании заказа; продакшен Dockerfile без заявленных в CMD зависимостей; гонки по остаткам при доставке.

## 3. Критические замечания

**Статус:** пункты 3.1–3.4 устранены в коде: цены и `total_amount` пересчитываются из каталога в `OrderCreateSerializer.validate()`; в `requirements.txt` добавлены `gunicorn` и `python-json-logger`; healthcheck в `Dockerfile` и `docker-compose.yml` переведён на `urllib`; для доставки вызывается `Stock.reserve_for_delivery()` в одной транзакции с заказом.

### 3.1. Цены позиций заказа берутся из запроса клиента (подделка суммы)

- **Где:** `backend/apps/orders/serializers.py` — `OrderItemCreateSerializer` (поле `price`), `backend/apps/orders/views.py` — создание `OrderItem` с `price=it["price"]`.
- **Суть:** Сервер доверяет `price` и `total_amount`, при этом сверяет `total_amount` только с **переданными** позициями, а не с актуальными ценами из БД.
- **Последствия:** Покупка по заниженной цене, манипуляция маржой и отчётностью — классическая уязвимость интернет-магазина.
- **Исправление:** На этапе валидации/транзакции для каждого `product_id` загружать `Product` и подставлять **только** `product.price` (и скидки/промо — отдельным серверным правилом). Клиенту можно возвращать расчёт, но не принимать цену как истину.

### 3.2. Продакшен Docker: `gunicorn` и `requests` не объявлены в зависимостях

- **Где:** `backend/Dockerfile` — `CMD ["gunicorn", ...]` и `HEALTHCHECK` с `import requests`; файлы `backend/requirements.txt` и `backend/requirements-dev.txt` — **без** `gunicorn` и `requests`.
- **Суть:** Образ, собранный только из заявленных requirements, с высокой вероятностью **не запустит** процесс и/или healthcheck.
- **Последствия:** Нерабочий или «ложноздоровый» деплой в контейнере.
- **Исправление:** Добавить `gunicorn` в production-зависимости; для healthcheck предпочтительно `curl` в образе или встроенный `urllib` без лишней зависимости.

### 3.3. Production logging: `pythonjsonlogger` не в requirements

- **Где:** `backend/config/settings/production.py` — formatter `'()': 'pythonjsonlogger.jsonlogger.JsonFormatter'`.
- **Суть:** Пакет `python-json-logger` не указан в `requirements.txt`.
- **Последствия:** При включении file-handler с JSON-форматтером — `ImportError` при старте приложения.
- **Исправление:** Добавить зависимость или сменить formatter на встроенный.

### 3.4. Заказы с доставкой: нет атомарного резерва остатков при создании

- **Где:** `backend/apps/orders/views.py` — `Stock.reserve_atomic` вызывается только для `DELIVERY_PICKUP`; для доставки выполняется лишь предварительная агрегированная проверка `Sum(quantity - reserved_quantity)`.
- **Суть:** Между проверкой и оплатой/комплектацией возможны параллельные заказы, уводящие остаток в минус на уровне бизнес-процесса.
- **Последствия:** Overselling, отмены заказов, нагрузка на поддержку.
- **Исправление:** Ввести единую политику: либо резерв на складе/в хабе при подтверждении, либо очередь заказов с блокировкой строк `Stock` (`select_for_update`) в одной транзакции с заказом — в духе уже существующего `reserve_atomic`.

### 4.1. Хранение JWT в `localStorage`

- **Где:** `frontend/src/lib/storage/token-storage.ts`, использование в `frontend/src/lib/api/client.ts`.
- **Последствия:** При любой XSS токены читаются скриптом; это противоречит строгим практикам для e-commerce.
- **Рекомендация:** HttpOnly Secure cookies (с CSRF-стратегией для API) или комбинированная схема; минимизация XSS поверхностью (CSP на стороне Next.js, санитизация контента).

### 4.2. Публичная Swagger/ReDoc схема API

- **Где:** `backend/config/urls.py` — `/api/docs/`, `/api/schema/`.
- **Последствия:** Упрощение разведки API для атакующего (массовый перебор, поиск слабых эндпоинтов).
- **Рекомендация:** В production ограничить по IP/VPN, Basic Auth, или отключить; отдельная внутренняя сборка документации.

### 4.3. Отслеживание заказа и оценка: риск перечисления и слабая привязка телефона

- **Где:** `backend/apps/orders/views.py` — `OrderTrackView`, `OrderRateView` (ранее `phone__icontains`; заменено на нормализованное сравнение).
- **Последствия:** Подбор пар order_number + phone; частичное совпадение телефона в строке.
- **Рекомендация:** Нормализованный телефон в БД, точное сравнение, rate limit, капча при множественных неудачах, маскирование ответа.

### 4.4. `RegisterView` и JWT endpoints с `csrf_exempt`

- **Где:** `backend/apps/users/views.py`, `backend/apps/users/urls.py`.
- **Суть:** Для session-cookie CSRF критичен; при JWT в заголовке риск ниже, но смешение с `SessionAuthentication` в `REST_FRAMEWORK` требует дисциплины на фронте.
- **Рекомендация:** Явно документировать модель угроз; не хранить чувствительное в cookie без CSRF-токена.

### 4.5. Файл `backend/.pgpass` в репозитории (untracked в статусе, но присутствует)

- **Где:** корень backend; `.gitignore` **не** содержит `.pgpass`.
- **Последствия:** Случайный `git add` раскрывает креды БД.
- **Рекомендация:** Добавить в `.gitignore`, использовать только секреты окружения/CI.

### 4.6. Дублирующийся маршрут `__debug__` в `urls.py`

- **Где:** `backend/config/urls.py` — два `path('__debug__/', ...)` подряд.
- **Последствия:** Первый маршрут перехватывает запросы; панель отладки может не работать; путаница при сопровождении.
- **Рекомендация:** Один корректный `include` без лишнего `RedirectView` на том же пути.

### 4.7. CSP в `SecurityHeadersMiddleware` с `'unsafe-inline'` и `'unsafe-eval'`

- **Где:** `backend/config/middleware.py`.
- **Суть:** Для JSON API заголовок CSP почти не даёт пользы; для HTML-ответов Django — ослабляет защиту.
- **Рекомендация:** Разделить политики для HTML и API; ужесточить для админки/шаблонов.

### 4.8. CI бэкенда: `mypy` и часть flake8 не блокируют сборку

- **Где:** `.github/workflows/backend-ci.yml` — `mypy ... || true`; flake8 второй проход с `--exit-zero`.
- **Последствия:** Ошибки типов и стиля проходят в main.
- **Рекомендация:** Убрать `|| true` для обязательных качественных ворот или ввести отдельный неблокирующий job.

### 4.9. CI фронтенда: вызовы несуществующих скриптов и `|| true`

- **Где:** `.github/workflows/frontend-ci.yml` — `npm run format:check`, `npm run type-check` (в `frontend/package.json` **нет** таких script), плюс `|| true` на lint/test.
- **Последствия:** Pipeline «зелёный» без реальной проверки.
- **Рекомендация:** Добавить scripts или поправить workflow; убрать безусловное игнорирование ошибок на обязательных шагах.

### 4.10. Версия Node в CI (18) vs стек Next 16 / React 19

- **Где:** `frontend/package.json` (next `16.1.6`), workflow Node `18`.
- **Последствия:** Расхождение с рекомендуемым runtime, потенциальные сбои сборки в CI при обновлении Next.
- **Рекомендация:** Зафиксировать LTS (20/22) в alignment с документацией Next.

### 4.11. Идемпотентность заказа на LocMem-кэше в dev

- **Где:** `backend/config/settings/development.py` — при отсутствии Redis кэш LocMem; `OrderListCreateView` использует кэш для idempotency.
- **Последствия:** При нескольких воркерах gunicorn в проде без общего Redis — идемпотентность ломается (это уже prod-конфигурация; в dev менее критично).
- **Рекомендация:** Документировать требование общего кэша для idempotency в prod.

### 4.12. Состояние `useAuth`: `hasToken` только при монтировании

- **Где:** `frontend/src/lib/hooks/useAuth.ts` — `useEffect` один раз выставляет `hasToken`.
- **Последствия:** После логина без перезагрузки страницы запрос `/auth/me/` может не запуститься до обновления состояния (зависит от того, вызывается ли инвалидация/сеттер снаружи).
- **Рекомендация:** Явно инвалидировать query и обновлять флаг токена после `login`/`register` (например, через событие или общий auth store).

## 6. Низкий приоритет / косметика

- `X-XSS-Protection` устаревает в современных браузерах; полезность низкая.
- Корневой редирект сайта Django `'' → /api/docs/` — для публичного домена бэкенда может быть нежелателен (но при раздельном хостинге с Next — ок).
- Дублирование импорта `Product` внутри методов во `views.py` (читаемость).
- В `ProductListView.get_queryset` локальный импорт `Stock` — мелочь для линтера.

## 8. Рекомендации по архитектуре (системные)

1. **Слой «оформление заказа»** оформить как единый application service: валидация корзины, цены из БД, промокоды, резерв остатков, idempotency, публикация событий (Celery) — один вход, меньше расхождений.
2. **Явная модель доверия к клиенту:** никаких денежных полей из JSON без подписи или без сверки с серверным состоянием.
3. **Auth:** разделить публичный профиль и админские признаки; рассмотреть отдельный выпуск токенов для admin API с коротким TTL.
4. **Наблюдаемость:** связать Sentry release с CI; логи структурировать после исправления JSON formatter deps.
5. **Контракт API:** автогенерация типов для фронта из OpenAPI (или zod-схемы из схемы) — уменьшит расхождения типов.
