# Полный анализ проекта Ringoo

**Дата анализа:** 2026  
**Цель:** простым языком описать, как устроена система, что уже есть, какую нагрузку выдержит и какая защита от атак заложена.

---

## 1. Что это за проект и как он устроен

**Ringoo** — это интернет-магазин электроники (сеть во Владикавказе и Северной Осетии). Система состоит из двух частей:

- **Бэкенд (Django)** — принимает запросы, работает с базой данных, отправляет письма и SMS, считает бонусы и остатки. Отдаёт данные в виде REST API (JSON).
- **Фронтенд (Next.js)** — сайт, который видит пользователь: каталог, корзина, оформление заказа, личный кабинет. Фронтенд обращается к бэкенду по адресу вида `http://localhost:8000/api/v1/` (в проде — ваш домен).

Пользователь заходит на сайт (Next.js) → браузер запрашивает данные у Django API → Django читает/пишет PostgreSQL и Redis, при необходимости ставит задачи в Celery → ответ возвращается на фронт и отображается на странице.

## 2. Как работает бэкенд (по шагам)

### 2.1 Вход в систему

- **Вход по телефону (SMS):** пользователь вводит номер → бэкенд генерирует код, сохраняет его в Redis на 5 минут и (при настроенном провайдере) отправляет SMS через sms.ru или Twilio → пользователь вводит код → бэкенд выдаёт **JWT-токены** (access на 1 час, refresh на 7 дней). Refresh при следующем запросе можно обменять на новый access (старый попадает в чёрный список).
- **Парольная авторизация** в проекте не используется; пользователь = телефон (и опционально email).

Фронтенд хранит токены (например, в localStorage), при каждом запросе к API подставляет в заголовок: `Authorization: Bearer <access_token>`. Если access истёк, клиент сам вызывает `POST /api/v1/auth/token/refresh/` с refresh-токеном и повторяет запрос.

### 2.2 Каталог товаров

- **Список:** `GET /api/v1/products/products/` — фильтры: категория, цена (мин/макс), поиск по названию и артикулу, «только в наличии», сортировка. Ответ кэшируется в Redis на 5 минут; при изменении товара или категории кэш сбрасывается по сигналу.
- **Автодополнение:** `GET /api/v1/products/autocomplete/?q=...` — до 10 товаров по запросу.
- **Карточка товара:** `GET /api/v1/products/products/<slug>/` — полное описание, фото, характеристики, наличие по магазинам.
- **Категории:** `GET /api/v1/products/categories/` — дерево категорий, кэш 10 минут.

Запросы к списку и категориям оптимизированы: используются `select_related` и `prefetch_related`, в базе есть индексы (в том числе составные по `is_active`, категории и дате).

### 2.3 Корзина

- Корзина привязана к пользователю (если он залогинен) или к гостевой сессии (session_key в Redis).
- При логине гостя корзина по сессии объединяется с корзиной пользователя (сигнал `merge_cart_on_login`).
- API: получить/создать корзину, добавить позицию, изменить количество, удалить позицию, очистить корзину. Проверяется наличие на складе при добавлении и при создании заказа.

### 2.4 Заказы

- **Создание:** `POST /api/v1/orders/` — из тела запроса или «из корзины» (`from_cart: true`). Вся операция (создание заказа, позиций, резерв остатков на складе, очистка корзины) выполняется в **одной транзакции**. Резерв остатков делается атомарно (через `F()` и `UPDATE`), чтобы два одновременных заказа не могли продать один и тот же остаток.
- После сохранения заказа в очередь Celery ставится задача `send_order_notifications(order_id)`. Сейчас в коде эта задача — заглушка (не вызывает отправку email/SMS); сами функции `send_order_confirmation` и `send_order_status_change` в `integrations.email_service` реализованы и могут быть подключены в задаче.
- **Список заказов** — только для авторизованных (свои заказы) или для staff (все). **Отслеживание по номеру и телефону:** `GET /api/v1/orders/track/?order_number=...&phone=...` — без авторизации.

### 2.5 Бонусы

- У пользователя есть бонусный счёт (модель BonusAccount). Начисление/списание идёт через сервис с атомарными операциями (`select_for_update`, F()). При подтверждении заказа бонусы начисляются по правилам (сигнал/вызов из логики заказа). API: посмотреть баланс и историю транзакций.

### 2.6 Магазины и остатки

- Справочник магазинов (адрес, координаты, часы работы), остатки по товарам (Stock). Резерв при самовывозе уменьшает доступное количество; при создании заказа резерв делается атомарно.

### 2.7 Избранное, акции, контент, CRM, оценка менеджеров

- **Избранное (wishlist):** модель «пользователь + товар», API: список, добавить, удалить.
- **Акции и промокоды:** модели Promotion, PromoCode; API акций и валидации промокода.
- **Контент:** блог (Article), новости (News), отзывы на товары (Review). API для списков и деталей.
- **CRM:** заявки «Не нашли товар» (MissingProductRequest) — сохранение в БД, при необходимости задача Celery для уведомления.
- **Оценка менеджеров:** по заказу один раз отправляется оценка 1–5 и комментарий (модель ManagerRating). Публичный endpoint даёт сводку: средняя оценка, количество, последние отзывы (без персональных данных). При указании `MANAGER_RATING_NOTIFY_EMAIL` на этот адрес уходит письмо через `send_manager_rating`.

### 2.8 База данных и кэш

- **PostgreSQL:** все основные данные (пользователи, товары, заказы, корзина, бонусы, магазины, контент и т.д.). В production задан `CONN_MAX_AGE=60`, чтобы переиспользовать соединения и снизить нагрузку при большом числе запросов.
- **Redis:** кэш списка товаров и категорий; сессии (вместо БД); брокер и бэкенд результатов для Celery; хранение SMS-кодов с TTL.

### 2.9 Очереди задач (Celery)

- В Docker подняты worker и beat. Задачи: пока в основном уведомления по заказу (заглушка) и при необходимости CRM/оценки. При подключении email/SMS в `send_order_notifications` тяжёлая рассылка не будет блокировать ответ API.

## 3. Как работает фронтенд

- **Next.js 16** (App Router), **React 19**, **TypeScript**, **Tailwind**, **Framer Motion**, **TanStack Query** (см. `frontend/package.json`).
- Адрес API задаётся переменными `NEXT_PUBLIC_API_V1_URL` или `NEXT_PUBLIC_API_URL`; по умолчанию — `http://localhost:8000/api/v1`.
- Единый **axios-клиент** (`lib/api/client.ts`): подставляет access-токен, при 401 пробует обновить токен через refresh и повторяет запрос, таймаут 10 секунд.
- Страницы: главная, каталог (с бесконечным скроллом и фильтрами), карточка товара, корзина, оформление заказа (степпер), отслеживание заказа, профиль, заказы, бонусы, магазины (с картой), блог, акции, промокоды, документы (оферта, конфиденциальность, реквизиты). Данные через React Query (кэш на клиенте, повторные запросы по ключам).
- Карты и подсказки адреса — Yandex Maps / Suggest (ключ из `NEXT_PUBLIC_YANDEX_MAPS_API_KEY` и т.п.).

## 4. Инфраструктура и деплой

- **Docker Compose:** сервисы `db` (PostgreSQL 15), `redis`, `web` (Django), `celery`, `celery-beat`. Volumes для данных БД, Redis, статики и медиа. Сеть одна, порты прокинуты (БД, Redis, backend 8000).
- Фронтенд в compose не описан — обычно крутят отдельно (`npm run dev` или выкладка на хостинг).
- **Production-настройки Django:** DEBUG выключен, ALLOWED_HOSTS и CORS из env, HTTPS (SECURE_SSL_REDIRECT и т.д.), HSTS, безопасные куки, статика через WhiteNoise или S3, логи в файл (путь через `LOG_FILE_PATH`).
- **CI (GitHub Actions):** отдельные пайпы для backend и frontend (линт, тесты); бэкенд поднимает PostgreSQL и Redis в сервисах и гонит тесты.

## 5. Какую нагрузку может выдержать (оценка)

- **Текущая конфигурация** — один процесс Django (`runserver` в dev, в проде обычно gunicorn/uwsgi с несколькими воркерами), одна БД, один Redis, один Celery worker.
- **Ограничения по скорости ответа:**
  - Список товаров и категорий отдаются из Redis при попадании в кэш — выдерживают много запросов в секунду с одного инстанса.
  - Остальные запросы (карточка товара, корзина, заказы, авторизация) идут в PostgreSQL; при нормальных индексах и `CONN_MAX_AGE` один инстанс Django может обслуживать порядка **сотен запросов в секунду** к БД без деградации (зависит от железа и сложности запросов).
- **Узкие места при росте:**
  - Один процесс Django — ограничение по CPU и одновременным запросам.
  - Один PostgreSQL без реплик — весь read/write на один инстанс.
  - Поиск по каталогу через `LIKE`/`icontains` по мере роста каталога станет тяжёлым; имеет смысл вынести в полнотекстовый поиск (PostgreSQL full-text или Elasticsearch).
- **Что уже заложено под нагрузку:** кэш списков, индексы в БД, пул соединений к БД, атомарные операции с остатками и бонусами, вынос уведомлений в Celery. Для **нескольких тысяч посетителей в день** и **десятков заказов в час** такой контур достаточен. Для «Чёрной пятницы» с пиками нужны: несколько воркеров приложения за балансировщиком, при необходимости реплика БД для чтения, отдельный пул/очереди для тяжёлых задач.

## 6. Защита от атак и безопасность

### 6.1 Аутентификация и доступ

- API в основном по JWT (Bearer). Сессии используются для админки и при необходимости для cookie-based сценариев. Пароли не используются для входа в магазин (только SMS-код).
- Права: каталог, магазины, контент, акции, отслеживание заказа, оценка менеджера, рейтинг — доступны без авторизации там, где так задумано. Корзина, заказы (создание/список/детали), бонусы, избранное, профиль — с проверкой пользователя или с ограничением по данным (например, заказы только свои, кроме staff).

### 6.2 Ограничение частоты запросов (rate limiting)

- **Общее API:** аноним — 100 запросов/час, авторизованный — 1000/час (лимиты DRF по scope `anon`/`user`).
- **Чтение каталога/категорий/магазинов:** отдельные классы с повышенными лимитами: аноним 300/час, пользователь 2000/час.
- **SMS-код:** 1 запрос в минуту с одного IP (throttle по IP). Дополнительные ограничения по номеру телефона реализованы в сервисе (Redis, TTL).

Это снижает риск перебора кодов, спама запросами и простого DDoS по API.

### 6.3 Заголовки безопасности и CORS

- В ответах выставляются: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `X-XSS-Protection: 1; mode=block`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (ограничение доступа к геолокации, микрофону, камере), базовая **Content-Security-Policy** (default-src 'self', script/style/img/font/connect — при необходимости CSP расширяют под скрипты фронта).
- **CORS:** разрешены только домены из `CORS_ALLOWED_ORIGINS` (в проде — явный список). Credentials разрешены там, где нужны куки.

### 6.4 Production

- Включены: редирект на HTTPS, Secure для cookie сессии и CSRF, HSTS (1 год, subdomains, preload), X-Frame-Options DENY. Секреты и ключи БД/Redis/SMS/email — из переменных окружения, не захардкожены.

### 6.5 Защита данных и мониторинг

- **Sentry:** при включённом DSN ошибки отправляются в Sentry; перед отправкой из запросов и пользовательских данных вырезаются пароли, токены, номера карт и т.п. (`before_send`). В проде так снижается риск утечки чувствительных данных в трекер ошибок.
- **CSRF:** включён для сессионных запросов; для чисто JWT-запросов с фронта CSRF не требуется, так как куки сессии не используются для API.

### 6.6 Целостность данных

- Создание заказа и резерв остатков — в одной транзакции, резерв через атомарный UPDATE по остаткам, чтобы исключить двойную продажу при гонках.
- Списание/начисление бонусов — в транзакциях с блокировкой строки (select_for_update).

Чего **нет** в текущем описании (и при желании можно усилить): отдельный WAF, ограничение размера тела запроса на уровне прокси, явная защита от массового перебора паролей (паролей в магазине нет), регулярные сканы уязвимостей (например, OWASP). Для типичного регионального магазина текущего масштаба описанной защиты достаточно; при росте и приёме платежей онлайн стоит добавить PCI-ориентированные меры и аудит.

## 7. Краткая сводка: что есть и что можно улучшить

| Область | Что есть | Что можно улучшить |
|--------|----------|---------------------|
| **Бэкенд** | Django 5, DRF, JWT, SMS-вход, каталог, корзина, заказы (с транзакцией и атомарным резервом), бонусы, магазины, избранное, акции, контент, CRM, оценка менеджеров, кэш списков, индексы БД | Подключить отправку email/SMS в задаче `send_order_notifications`; при росте каталога — полнотекстовый поиск |
| **Фронтенд** | Next.js 16 / React 19, каталог, корзина, оформление заказа, профиль, заказы, бонусы, магазины, блог, акции, карты, единый API-клиент с refresh токена | Использовать единый env для API URL в проде; при необходимости — страница «О нас» с рейтингом из `ratings-summary` |
| **Инфраструктура** | Docker Compose (БД, Redis, web, Celery, beat), production-настройки, логи, опционально S3 | В проде — gunicorn/uwsgi, Nginx перед приложением, отдельный контур для фронта; при росте — несколько воркеров, реплика БД |
| **Нагрузка** | Кэш, индексы, пул соединений БД, атомарные операции | Нагрузочное тестирование (Locust/JMeter), план масштабирования при пиках |
| **Безопасность** | JWT, CORS, security headers, rate limit, Sentry с фильтром данных, HTTPS/HSTS в проде | При приёме платежей — PCI DSS; при необходимости — WAF, лимит размера запроса |

Документ можно использовать как единую «карту» проекта для онбординга разработчиков и для планирования доработок под нагрузку и безопасность.
