## 2. Критические недоработки (исправить в первую очередь)

### 2.1 Создание заказа без транзакции и блокировок

**Файл:** `backend/apps/orders/views.py` (OrderListCreateView.post).

**Проблема:** Создание заказа, позиций, резервирование остатков и очистка корзины выполняются **без** `transaction.atomic()`. При сбое после сохранения заказа (например, ошибка при резерве или при отправке уведомления) возможны:
- создан заказ, но остатки не зарезервированы;
- корзина очищена, заказ не создан.

**Риск:** Потеря консистентности данных, двойная продажа остатка.

**Решение:**
- Обернуть всю логику создания заказа (проверка остатков → создание Order/OrderItem → резерв Stock → очистка корзины) в одну `transaction.atomic()`.
- Резервирование остатков выполнять внутри этой же транзакции с `select_for_update()` по строкам `Stock`, чтобы исключить гонку при двух одновременных заказах на один и тот же остаток.

**Статус:** [x] Сделано (transaction.atomic в OrderListCreateView.post, резерв через Stock.reserve_atomic).

---

### 2.2 Резервирование остатков (Stock) не атомарно

**Файл:** `backend/apps/stores/models.py` — метод `Stock.reserve(amount)`.

**Проблема:** Используется «прочитать → изменить → сохранить» без блокировки строки. Два одновременных заказа могут оба прочитать `available_quantity = 1`, оба вызвать `reserve(1)` и сохранить — резерв станет 2 при фактическом количестве 1.

**Решение:**
- Резервировать в БД атомарно: `Stock.objects.filter(pk=..., quantity__gte=F('reserved_quantity') + amount).update(reserved_quantity=F('reserved_quantity') + amount)` или аналог с `select_for_update()` и проверкой `available_quantity >= amount`, затем обновление.
- Вызывать резерв только внутри `transaction.atomic()` при создании заказа (п. 2.1).

**Статус:** [x] Сделано (Stock.reserve_atomic через F() и update в одной транзакции).

## 3. Соответствие ТЗ (пробелы и доработки)

### 3.1 Поиск по названию и артикулу (ТЗ: поле быстрого поиска с автодополнением)

**Сейчас:** В `ProductListView` поиск только по полю `title` (`title__icontains=search`).

**Нужно:**
- Добавить поиск по артикулу: `Q(title__icontains=search) | Q(sku__icontains=search)` (или точное совпадение по `sku`, если поиск по артикулу — точный).
- Автодополнение по ТЗ — отдельный endpoint (например, `GET /api/v1/products/autocomplete/?q=...`) с ограничением по числу результатов (5–10) и, при росте каталога, переход на полнотекстовый поиск (PostgreSQL full-text или Elasticsearch, см. PLAN Этап 4.3).

**Статус:** [x] Поиск по артикулу реализован (Q(title__icontains)|Q(sku__icontains)); [x] Автодополнение: `GET /api/v1/products/autocomplete/?q=...` (до 10 товаров).

---

### 3.2 Фильтр «наличие в магазинах» (ТЗ: панель фильтров)

**Сейчас:** В API списка товаров фильтра «есть в наличии хотя бы в одном магазине» нет.

**Нужно:** Добавить параметр, например `in_stock=true`: при `true` фильтровать товары, у которых есть хотя бы одна запись `Stock` с `quantity > reserved_quantity` (или использовать подзапрос/аннотацию).

**Статус:** [x] Реализовано (параметр in_stock=true, Exists(Stock с quantity > reserved_quantity)).

---

### 3.3 Избранные товары (ТЗ: в ЛК — история заказов, бонусы, избранные товары)

**Сейчас:** Модели «избранное» (Wishlist / избранные товары) в backend нет. В контенте есть поле `is_featured` у статей — к товарам не относится.

**Нужно:** Ввести модель избранного (например, `WishlistItem`: user + product) и API: добавить/удалить, список избранного. На фронте — раздел в ЛК и, при необходимости, кнопка на карточке товара.

**Статус:** [x] Реализовано: приложение `apps.wishlist`, модель `WishlistItem`, API `GET/POST /api/v1/wishlist/`, `DELETE /api/v1/wishlist/<product_id>/`.

---

### 3.4 Оценка менеджеров (ТЗ: рейтинг менеджеров в ЛК и в «О нас»)

**Сейчас:** Есть отправка письма с оценкой (`send_manager_rating`), шаблоны писем. Нет: хранения оценок в БД, API для отправки оценки и для чтения рейтинга, страницы «О нас» с рейтингом.

**Нужно:** Модель (например, `ManagerRating`: заказ, оценка, комментарий, менеджер опционально), API для отправки оценки (после заказа) и для отображения рейтинга (агрегат по менеджерам/общий), вывод в ЛК и на странице «О нас».

**Статус:** [x] Реализовано: модель `ManagerRating`, API `POST /api/v1/orders/rate/` (оценка по заказу), `GET /api/v1/orders/ratings-summary/` (средняя, количество, последние отзывы), уведомление на email при `MANAGER_RATING_NOTIFY_EMAIL`.

## 4. Высокая нагрузка и масштабируемость

### 4.1 База данных

- **Connection pooling:** В `config/settings/base.py` (и production) для PostgreSQL не задан `CONN_MAX_AGE`. Для снижения накладных расходов на соединения задать разумное значение (например, 60–120 сек) или вынести пул в pgbouncer и документировать.
- **Индексы:** Для списка товаров с фильтрами имеет смысл проверить составные индексы (например, `(is_active, category_id, created_at)` или по полям сортировки/фильтрации), чтобы тяжёлые списки не сканировали лишнее. При росте каталога — обязательны.
- **Партиционирование:** Для этапа highload — план партиционирования больших таблиц (например, Order, OrderItem, логи) по дате; пока можно зафиксировать в плане на будущее.

**Статус:** [x] CONN_MAX_AGE задан в production (60 сек, DB_CONN_MAX_AGE); [x] Составные индексы Product: (is_active, category), (is_active, -created_at); [ ] Партиционирование — в дорожную карту.

### 4.2 Поиск при росте каталога

**Сейчас:** Поиск по `title`/`sku` через `icontains` в PostgreSQL. При десятках/сотнях тысяч товаров запросы будут тяжёлыми.

**Рекомендация:** Включить в план (как в PLAN Этап 4.3): PostgreSQL full-text search (tsvector) или Elasticsearch/OpenSearch для каталога и автодополнения, с кэшированием горячих запросов.

**Статус:** [ ] В плане; реализация — по приоритету после MVP.

## 5. Безопасность и эксплуатация

### 5.1 Production-настройки

- **Логирование:** В `config/settings/production.py` путь к логам вынесен в переменную окружения `LOG_FILE_PATH` (по умолчанию `/app/logs/django.log`). Каталог нужно создавать в entrypoint или задать путь в существующую директорию — см. комментарий в production.py.
- **INSTALLED_APPS:** В ветке `else` (без S3) выполняется `INSTALLED_APPS = ['whitenoise...'] + INSTALLED_APPS`. Убедиться, что при импорте `INSTALLED_APPS` из `base` не происходит дублирования и что порядок корректен (WhiteNoise в начале при необходимости).
- **Секреты:** Не хардкодить; все секреты из переменных окружения — ок; проверить, что в CI и деплое нет дефолтных паролей в prod.

**Статус:** [x] Логи — конфигурируемый LOG_FILE_PATH; [ ] INSTALLED_APPS — проверено при деплое.

### 5.2 Rate limiting и SMS
