# План разработки административной панели Ringoo

Документ описывает полный план реализации админ-панели для управления сайтом: контент (товары, категории, статьи), заказы, аналитика (выручка, заказы), пользователи, магазины, акции и сопутствующие функции.

---

## 1. Текущее состояние

### 1.1 Что уже есть

| Область | Реализация | Где |
|--------|-------------|-----|
| **Товары и каталог** | CRUD через Django Admin | `apps/products/admin.py`: Category, Product, ProductImage, ProductSpec |
| **Заказы** | Просмотр, смена статуса, экспорт CSV | `apps/orders/admin.py`: Order, OrderItem, ManagerRating |
| **Пользователи** | CRUD, профиль, адреса | `apps/users/admin.py`: CustomUser, UserProfile, DeliveryAddress |
| **Магазины и остатки** | Магазины, менеджеры, Stock | `apps/stores/admin.py`: Store, Manager, Stock |
| **Контент** | Статьи, новости, отзывы, теги | `apps/content/admin.py`: Tag, Article, News, Review |
| **Бонусы** | Счета и транзакции | `apps/bonus/admin.py`: BonusAccount, BonusTransaction |
| **Корзина** | Просмотр корзин и позиций | `apps/cart/admin.py`: Cart, CartItem |
| **Акции и промокоды** | Акции, промокоды | `apps/promotions/admin.py`: Promotion, PromoCode |
| **CRM** | Заявки «Не нашли товар» | `apps/crm/admin.py`: MissingProductRequest |
| **Избранное** | Просмотр избранного | `apps/wishlist/admin.py`: WishlistItem |

- Доступ к Django Admin: `/admin/` (логин staff/superuser).
- API для заказов для staff: список всех заказов (`GET /api/v1/orders/`), детали заказа; для остальных сущностей отдельные admin API либо нет (управление только через Django Admin).

### 1.2 Чего не хватает для «полной» админ-панели

- **Единый веб-интерфейс** под стиль сайта (сейчас только Django Admin).
- **Дашборд**: сводка по заказам, выручка, топ товаров, новые заказы.
- **Аналитика**: в плане учитывается только выручка (закупочной цены в системе нет).
- **Удобное управление заказами** из одного места (фильтры, смена статуса, печать/экспорт).
- **Управление товарами и остатками** без перехода в Django (опционально): создание/редактирование товаров, категорий, загрузка фото, остатки по магазинам.
- **Роли и права**: разграничение (например, менеджер только заказы, контент-менеджер — товары и контент) — при необходимости.

## 2. Цели админ-панели

1. **Заполнение контентом**: категории, товары (в т.ч. фото, характеристики, остатки), акции, статьи/новости.
2. **Управление заказами**: список, фильтры, смена статуса, детали, экспорт, при необходимости — печать.
3. **Отслеживание продаж и выручки**: выручка за период, количество заказов, средний чек (закупочной цены нет — считаем только выручку).
4. **Пользователи и бонусы**: просмотр/редактирование пользователей, адресов, бонусных счетов и ручные корректировки.
5. **Магазины и наличие**: магазины, остатки по товарам, менеджеры.
6. **Контент и маркетинг**: статьи, новости, отзывы (модерация), акции, промокоды.
7. **CRM**: заявки «Не нашли товар», статусы, ответы.

## 3. Варианты реализации

### Вариант A: Только доработка Django Admin + отчёты

- **Плюсы**: быстрее, без отдельного фронта.
- **Минусы**: интерфейс не под бренд, дашборд и графики нужны отдельно (например, через django-admin-charts или кастомные views в admin).
- **Подходит**, если достаточно стандартного админского интерфейса и пары отчётов (CSV/Excel).

### Вариант B: Отдельное SPA админки (Next.js) + Admin API

- **Плюсы**: единый стиль с сайтом, гибкий дашборд, удобные формы и фильтры, мобильная адаптация.
- **Минусы**: больше разработки (API для админки + фронт).
- **Подходит**, если нужна «полноценная» админ-панель с дашбордом и удобным UX.

### Вариант C: Гибрид

- Оставить Django Admin для части сущностей (например, пользователи, права, теги).
- Реализовать отдельный дашборд и разделы «Заказы», «Товары», «Аналитика» в Next.js с вызовом Admin API.

**Рекомендация**: Вариант B или C. Ниже план ориентирован на **вариант B** (полноценная админка на Next.js + API); при выборе C часть пунктов можно выполнять только для выбранных разделов.

## 4. Этапы реализации

### Этап 0: Подготовка (Backend — API и права) — **ВЫПОЛНЕНО**

Цель: дать фронту админки все нужные данные и действия через API с проверкой `is_staff`.

Префикс Admin API: **`/api/v1/admin/`**

| № | Задача | Детали |
|----|--------|--------|
| 0.1 | **Permission для Admin API** | Ввести permission-класс `IsStaff` (или использовать `IsAdminUser`) и применять ко всем admin API. |
| 0.2 | **Admin API: Заказы** | Уже есть список/детали для staff. Добавить: `PATCH /api/v1/orders/{id}/` — смена статуса, опционально комментарий для менеджера. Сериализатор только для полей status (и при необходимости comment). |
| 0.3 | **Admin API: Товары** | CRUD для товаров и категорий (или расширить существующие): создание/обновление/удаление Product, Category; загрузка изображений (ProductImage). Использовать существующие сериализаторы/views или добавить admin-варианты с `IsStaff`. |
| 0.4 | **Admin API: Остатки (Stock)** | Список/фильтр по товару или магазину; `PATCH` остатков (quantity, при необходимости reserved_quantity). Endpoint вида `GET/PATCH /api/v1/admin/stores/stock/` или по store/product. |
| 0.5 | **Admin API: Пользователи** | Список пользователей (пагинация, поиск по phone/email), детали пользователя, опционально PATCH (is_active, is_staff). Адреса доставки и бонусный счёт — только чтение или через отдельные endpoints. |
| 0.6 | **Admin API: Бонусы** | Список счетов, детали счёта и транзакции; endpoint ручного начисления/списания (например, `POST /api/v1/admin/bonus/accounts/{id}/adjust/` с amount и reason=admin_adjust). |
| 0.7 | **Admin API: Контент** | CRUD для Article, News, Tag; модерация Review (одобрение/отклонение). Использовать существующие модели и сериализаторы, добавить admin-views с IsStaff. |
| 0.8 | **Admin API: Магазины** | Список/детали Store, CRUD при необходимости; список менеджеров, привязка к магазину. |
| 0.9 | **Admin API: Акции и промокоды** | CRUD Promotion, PromoCode (или только чтение + создание/редактирование через существующие модели). |
| 0.10 | **Admin API: CRM** | Список заявок MissingProductRequest, смена статуса, опционально комментарий менеджера. |
| 0.11 | **Admin API: Дашборд (аналитика)** | Endpoint вида `GET /api/v1/admin/dashboard/stats/` с агрегатами: количество заказов за период, сумма выручки (total_amount), средний чек; топ N товаров по количеству проданных единиц; количество новых заказов за сегодня/неделю. Опционально: по магазинам, по статусам. |

**Примечание:** Закупочной цены в системе нет — в аналитике и дашборде считаем только выручку.

**Реализовано:**
- `apps.admin_api` — приложение Admin API
- `IsStaff` permission (доступ только `is_staff=True`)
- `GET /api/v1/admin/dashboard/stats/` — дашборд (заказы, выручка, топ товаров)
- `PATCH /api/v1/admin/orders/{id}/` — смена статуса заказа
- `GET/PATCH /api/v1/admin/products/`, `products/{id}/`, `products/{id}/patch/`, `products/categories/`
- `GET /api/v1/admin/stores/stock/`, `PATCH stores/stock/{id}/` — остатки
- `GET/PATCH /api/v1/admin/users/`, `users/{id}/`, `users/{id}/patch/`
- `GET /api/v1/admin/bonus/accounts/`, `accounts/{id}/`, `POST accounts/{id}/adjust/`
- `GET /api/v1/admin/content/tags/`, `articles/`, `news/`, `reviews/`, `PATCH reviews/{id}/patch/`
- `GET /api/v1/admin/stores/`, `promotions/`, `promocodes/`
- `GET/PATCH /api/v1/admin/crm/requests/`, `requests/{id}/`, `requests/{id}/patch/`

- `/admin` — дашборд: карточки (заказы сегодня/неделю/месяц, выручка, средний чек), топ товаров

## 5. Технические рекомендации

### 5.1 Backend (Django)

- Все admin endpoints под префиксом, например `/api/v1/admin/` (или отдельный URLconf для admin API).
- Permission: `IsAuthenticated` + `IsAdminUser` (или кастомный `IsStaff`).
- Для дашборда и отчётов использовать аннотации и агрегаты ORM (Sum, Count), при больших объёмах — кэш (Redis) с TTL.
- Загрузка файлов (изображения товаров, категорий, акций): через multipart/form-data; сохранять в MEDIA, отдавать URL в ответе (как уже сделано для товаров).

### 5.2 Frontend (Next.js)

- Роуты админки: `src/app/admin/` (или `src/app/dashboard/`) — layout с проверкой is_staff, редирект неавторизованных на `/admin/login`.
- Использовать те же TanStack Query и apiClient; для admin API передавать те же заголовки (JWT).
- Таблицы: единый компонент таблицы с сортировкой и пагинацией; фильтры вынести в общие компоненты.
- Формы: создание/редактирование товара, заказа, пользователя — отдельные страницы или модалки; валидация на клиенте и вывод ошибок с API.

### 5.3 Безопасность

- Не отдавать в API админки чувствительные поля (например, хэш пароля); при необходимости «сброс пароля» — отдельный endpoint с отправкой письма/смс.
- Логирование действий админа (кто что изменил) — опционально, отдельная задача (audit log).

## 6. Порядок внедрения (краткий)

1. **Этап 0** — Admin API (заказы PATCH, дашборд stats, при необходимости товары/категории/остатки, пользователи, бонусы, контент, магазины, акции, CRM).
2. **Этап 1** — Фронт: вход, layout, дашборд, меню.
3. **Этап 2** — Заказы (список, фильтры, детали, смена статуса, экспорт).
4. **Этап 3** — Каталог (категории, товары, изображения, остатки).
5. **Этапы 4–8** — по приоритету: пользователи и бонусы → контент и маркетинг → магазины и остатки → CRM → расширенная аналитика по выручке.
