# Платежи и PCI DSS (Ringoo)

Краткая фиксация для ТЗ и аудита: готового приёма карт в репозитории может не быть; интеграция — отдельный этап.

## Принципы

1. **Полные номера карт (PAN) и CVC** не хранятся и не логируются на стороне Ringoo. Данные карты вводит пользователь в **виджете/хостинге платёжного провайдера** (или редирект на оплату у провайдера).
2. **Токенизация** — на стороне провайдера. В нашей БД допустимы только **нечувствительные** идентификаторы: id платежа, id заказа у провайдера, статус, маска карты (если отдаёт провайдер), срок действия в обезличенном виде — строго по документации провайдера.
3. **Webhook / callback** от провайдера:
   - только по **HTTPS**;
   - проверка **подписи** (HMAC, RSA или иной механизм из документации провайдера);
   - **идемпотентность** обработки (повтор одного уведомления не меняет состояние заказа дважды);
   - ответ провайдеру — по его спецификации (часто `200` с фиксированным телом).
4. **Сервер–сервер**: секреты провайдера (API keys, webhook secret) только в **переменных окружения** / секрет-хранилище, не в репозитории.
5. **Фронтенд** не должен получать «секреты мерчанта»; только публичные ключи, если провайдер так предусматривает.

## Чеклист перед приёмом реальных платежей

- [ ] Выбран провайдер и подписан договор / пройдена модерация.
- [ ] Реализованы сценарии: успех, отказ, таймаут, повтор webhook.
- [ ] Логи без PAN/CVC; маскирование при необходимости показа в ЛК.
- [ ] Юридические документы (оферта, политика ПДн) согласованы с способом оплаты.

Подробный перечень рисков — в `docs/SECURITY.txt` (в т.ч. контекст PCI).
