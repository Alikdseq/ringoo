# План доработок Ringoo

Документ описывает задачи по исправлению ошибок и недочётов, сформулированные профессионально и разбитые на атомарные шаги. Выполнять по шагам: вы присылаете номер шага — выполняю реализацию.

---

## Блок 1: Корзина

**Проблема:** При нажатии «В корзину» в каталоге анимация срабатывает, но в корзине товаров нет. Требуется: реальное добавление/удаление, изменение количества, хранение (сессия для гостей, БД для авторизованных), очистка после заказа.

| Шаг | Задача | Детали |
|-----|--------|--------|
| **1.1** | Подключить добавление в корзину в карточке товара (каталог) | В `ProductCard`: по клику «В корзину» вызывать API `POST /api/v1/cart/items/` (product_id, quantity), после успеха — инвалидировать запрос корзины и показывать анимацию. Обработка ошибок (нет в наличии и т.д.). |
| **1.2** | Подключить добавление в корзину на странице товара (PDP) | На странице `/products/[slug]` кнопка «В корзину» уже вызывает `addToCart` — проверить, что передаётся `product.id` (UUID), quantity, опционально store_id; при успехе инвалидировать корзину. |
| **1.3** | Обеспечить хранение корзины для гостей (сессия) | Backend: корзина по `session_key` уже реализована. Frontend: убедиться, что запросы к API идут с `withCredentials: true` и что бэкенд отдаёт и сохраняет session cookie; при первом добавлении в корзину сессия создаётся. |
| **1.4** | Синхронизация корзины при авторизации | Backend: при логине объединять корзину по session_key с корзиной пользователя (уже есть сигнал `merge_cart_on_login`). Frontend: после успешного входа инвалидировать запрос корзины и обновить UI. |
| **1.5** | Страница корзины: изменение количества и удаление | На `/cart` при изменении количества вызывать `PATCH /api/v1/cart/items/{id}/`, при удалении — `DELETE`. Обновлять локальный кэш (React Query) после каждого действия. |
| **1.6** | Очистка корзины после оформления заказа | После успешного `POST /api/v1/orders/` с `from_cart: true` бэкенд уже очищает корзину. Frontend: после успешного создания заказа инвалидировать запрос корзины и перенаправить на страницу успеха заказа. |

## Блок 2: Переход в категорию с главной

**Проблема:** При клике на категорию (Apple, Наушники и т.д.) на главной открывается общий каталог без выбранной категории.

| Шаг | Задача | Детали |
|-----|--------|--------|
| **2.1** | Инициализировать фильтр «категория» из URL на странице каталога | На `/catalog` при монтировании читать `searchParams.get('category')` и записывать в state `category`, чтобы при переходе по ссылке `/catalog?category=apple` сразу отображались товары только этой категории. |

## Блок 3: Профиль и форма входа/регистрации

**Проблема:** На странице «Профиль» должен отображаться ЛК для авторизованных; для неавторизованных — форма входа и возможность регистрации.

| Шаг | Задача | Детали |
|-----|--------|--------|
| **3.1** | Форма входа в ЛК | Страница входа (например `/login`): поле телефона, запрос SMS-кода, поле кода, отправка на `POST /api/v1/auth/sms/verify/`, сохранение токенов и редирект в профиль или на предыдущую страницу. |
| **3.2** | Форма регистрации (первый вход по SMS) | Регистрация как «первый вход по телефону»: тот же поток SMS request → verify; бэкенд создаёт пользователя при verify, если его ещё нет. Отдельная страница `/register` с тем же потоком или объединённая с логином. |
| **3.3** | Редирект неавторизованных с профиля на вход | На `/profile`: если пользователь не авторизован (нет токена / 401 от `/api/v1/auth/me/`), перенаправлять на `/login` с `?next=/profile`. После входа редирект на `next`. |
| **3.4** | Отображение ЛК для авторизованных на /profile | На `/profile` при успешном `/auth/me/` показывать: приветствие, данные профиля, ссылки на заказы, бонусы, избранное, адреса доставки, выход. |

## Блок 4: Полноценный личный кабинет

**Проблема:** ЛК нужно реализовать полностью: регистрация/авторизация (email или телефон), восстановление пароля, история заказов, адреса, избранное.

| Шаг | Задача | Детали |
|-----|--------|--------|
| **4.1** | Авторизация по телефону (SMS) | Реализовано в бэкенде. Frontend: страница входа с запросом кода и верификацией (см. шаг 3.1). |
| **4.2** | Авторизация по email (опционально) | Если в ТЗ требуется вход по email: бэкенд — endpoint выдачи ссылки/кода на email и проверка; фронт — форма «Войти по email». Иначе оставить только телефон. |
| **4.3** | Восстановление пароля | Если используется пароль (email-логин): «Забыли пароль» → ввод email → отправка ссылки/кода → форма нового пароля. Если только SMS — восстановление не требуется. |
| **4.4** | История заказов с деталями | Страница `/orders`: список заказов (GET /api/v1/orders/). Страница `/orders/[id]`: детали заказа (GET /api/v1/orders/{id}/). Доступ только для авторизованных. |
| **4.5** | Сохранённые адреса доставки | Backend: модель DeliveryAddress уже есть. API: список/добавление/редактирование/удаление адресов. Frontend: раздел в профиле «Мои адреса» с формой и списком. |
| **4.6** | Избранное (список желаний) | Backend: API wishlist уже есть. Frontend: страница «Избранное» (например `/profile/wishlist` или `/wishlist`) — список, добавление с карточки товара, удаление. В шапке — иконка избранного и счётчик. |

## Блок 5: Валюта — рубли

**Проблема:** Отображается валюта тенге (₸), должна быть рубли (₽).

| Шаг | Задача | Детали |
|-----|--------|--------|
| **5.1** | Заменить отображение валюты на рубли | По всему фронту: заменить символ «₸» на «₽» (руб.). Проверить: карточки товаров, страница товара, корзина, оформление заказа, заказы в ЛК. При необходимости вынести подпись валюты в константу или i18n. |

## Блок 6: Карточка товара и переход на неё

**Проблема:** При клике на карточку товара показывается «Товар не найден». Нужна корректная страница товара с ЧПУ, названием, описанием, ценой, фото, наличием.

| Шаг | Задача | Детали |
|-----|--------|--------|
| **6.1** | Корректный запрос товара по slug и обработка 404 | Backend: GET `/api/v1/products/products/{slug}/` по slug уже отдаёт товар. Frontend: убедиться, что в API передаётся именно `slug` из URL; при 404 от бэкенда показывать «Товар не найден» с ссылкой в каталог (уже есть). Проверить CORS, baseURL, формат slug. |
| **6.2** | Страница товара: название, описание, цена, галерея фото | Убедиться, что на PDP выводятся: title, description, price, галерея изображений (уже через ProductMediaArea). При отсутствии данных не падать, показывать заглушки. |
| **6.3** | Наличие на странице товара | Выводить «В наличии» / «Нет в наличии» или остатки по складам (уже есть stock в ProductDetail). Если остатки по магазинам — показывать список магазинов с количеством. |
| **6.4** | ЧПУ для товаров и категорий | Товары: URL `/products/{slug}` (уже так). Категории: переход по `/catalog?category={slug}` (уже так). При необходимости добавить маршруты вида `/catalog/category/{slug}` и редирект на `/catalog?category={slug}`. |

## Блок 7: Оформление заказа

**Проблема:** Форма заказа, доставка, оплата, сохранение в БД и уведомление менеджеру должны работать корректно.

| Шаг | Задача | Детали |
|-----|--------|--------|
| **7.1** | Форма заказа: имя, телефон, email, адрес | На странице оформления заказа (checkout) все поля должны быть в форме и передаваться в `POST /api/v1/orders/`: full_name, phone, email, delivery_address (город, улица, дом, квартира, индекс при доставке). Валидация на фронте и бэкенде. |
| **7.2** | Выбор способа доставки | В форме: выбор «Самовывоз» или «Курьерская доставка». При самовывозе — выбор магазина (список/карта). При доставке — поля адреса. Передавать `delivery_type` и при доставке — `delivery_address`. |
| **7.3** | Выбор способа оплаты | В форме: наличные, картой при получении, онлайн (и т.д. по бэкенду). Передавать `payment_type` в создание заказа. |
| **7.4** | Сохранение заказа в БД | Уже реализовано: POST с `from_cart: true` или с массивом `items`. Проверить, что после успешного ответа корзина на фронте очищается (инвалидация) и редирект на страницу успеха. |
| **7.5** | Уведомление менеджеру при новом заказе | Backend: в задаче `send_order_notifications` подключить отправку email менеджеру (или в админку через сигнал). Настроить `MANAGER_EMAIL` или использовать существующий канал (например, письмо на админ-почту). |

## Блок 8: Поиск и фильтрация (масштабирование)

**Проблема:** При большом каталоге (>10 000 товаров) и сложных фильтрах нужен поиск через Elasticsearch/OpenSearch, динамические цены/остатки, сложные фильтры.

| Шаг | Задача | Детали |
|-----|--------|--------|
| **8.1** | Оценка и план внедрения поиска | Зафиксировать: при каком объёме включать Elasticsearch/OpenSearch; текущий поиск по PostgreSQL (title, sku, фильтр in_stock) оставить для малого каталога. Документировать план миграции на поисковый движок. |
| **8.2** | Сложные фильтры (диапазоны, мультивыбор, наличие) | На фронте и бэкенде: фильтр по диапазону цен уже есть; добавить при необходимости фильтр «в наличии» (in_stock), мультивыбор категорий или брендов. Backend: расширить параметры GET списка товаров; фронт — чекбоксы/чипы. |
| **8.3** | Динамические цены и остатки в реальном времени | Остатки уже отдаются из БД (Stock). Цены — из Product. При необходимости кэшировать с коротким TTL или отдавать из БД без кэша для критичных страниц. Группы пользователей и персональные цены — отдельная задача при появлении требований. |

## Порядок выполнения (рекомендуемый)

1. **Блок 5** (валюта) — быстрый фикс.  
2. **Блок 1** (корзина) — критично для конверсии.  
3. **Блок 2** (категория из URL) — быстрый фикс.  
4. **Блок 6** (страница товара и переход) — чтобы клик по карточке вёл на товар.  
5. **Блок 3 и 4** (вход, регистрация, ЛК) — для доступа к заказам и избранному.  
6. **Блок 7** (оформление заказа) — проверить и допилить поля и уведомления.  
7. **Блок 8** — по мере роста каталога и требований.

## Как работать по плану

- Вы пишете, например: «Шаг 1.1», «Шаг 5.1», «Выполни блок 1» — я делаю только указанные шаги.
- Можно просить несколько шагов подряд (например: «1.1, 1.2, 1.5»).
- После выполнения шага можно проверить сценарий и перейти к следующему.
