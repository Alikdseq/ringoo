# 🔐 Полный чек-лист безопасности для интернет-магазина Ringoo

## Введение
Данный документ представляет собой исчерпывающий список уязвимостей и направлений проверки безопасности для проекта Ringoo (Django + Next.js). Он составлен на основе лучших практик OWASP, требований PCI DSS (для приема платежей), российского законодательства (152-ФЗ) и типовых рисков e-commerce приложений.

Цель – дать команде разработки инструмент для самостоятельного аудита и устранения потенциальных проблем до выхода в продакшен.

## 1. Аутентификация и управление сессиями

### 1.1 SMS-аутентификация
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 1.1.1 | Хранение SMS-кода в Redis без TTL или с неверным временем жизни | Код может быть использован злоумышленником позже, даже после истечения срока | Код должен храниться с TTL 5 минут и удаляться после успешной верификации |
| 1.1.2 | Отсутствие rate limiting на запрос кода (по номеру телефона и IP) | Атака перебором кода, DoS, финансовые потери (оплата SMS) | Ограничить: не более 3 запросов в час на номер, не более 1 в минуту на IP |
| 1.1.3 | SMS-код передается в открытом виде в логах (например, при логировании запросов) | Утечка кода, компрометация аккаунта | Исключить логирование полей phone и code; использовать маскирование |
| 1.1.4 | Отсутствие проверки, что код принадлежит именно этому номеру (связка номер-код) | Возможность подмены номера, вход на чужой аккаунт | Ключ в Redis должен быть уникальным для номера и, возможно, сессии |
| 1.1.5 | Возможность повторной отправки кода без ограничений | Финансовые потери, раздражение пользователя | Внедрить механизм «отправить повторно можно через 60 секунд» |
| 1.1.6 | Нет защиты от автоматизированных ботов (captcha после нескольких неудачных попыток) | Перебор кодов, создание фейковых аккаунтов | Добавить reCAPTCHA или аналоги после 3 неудачных попыток |

### 1.2 JWT токены
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 1.2.1 | Access token хранится в localStorage / sessionStorage | XSS может украсть токен | Использовать httpOnly Secure cookie для access token (с ограничением времени) |
| 1.2.2 | Refresh token не ротируется при каждом использовании | Украденный refresh token может быть использован бесконечно | Реализовать refresh token rotation: при каждом обновлении выдавать новую пару, старый инвалидировать |
| 1.2.3 | Отсутствует проверка отзыва токенов (черный список) | Нет возможности принудительно завершить сессию | Хранить активные refresh токены в базе или Redis, проверять при обновлении |
| 1.2.4 | Алгоритм подписи слабый (HS256) или секрет короткий | Подделка токена | Использовать RS256 с закрытым/открытым ключами или длинный сложный секрет (не менее 32 символов) |
| 1.2.5 | Access token живет слишком долго (более 15 минут) | Риск компрометации выше | Время жизни access token – 15-30 минут, refresh token – 7-30 дней |
| 1.2.6 | Отсутствует проверка audience (aud) и issuer (iss) | Токен может быть использован в другом сервисе | Явно задавать aud и iss и проверять их |

### 1.3 Регистрация и профиль
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 1.3.1 | Возможность регистрации с уже существующим номером без подтверждения | Захват чужого аккаунта | Перед созданием аккаунта требуется верификация номера (код) |
| 1.3.2 | Отсутствие проверки на «сильные» пароли (для email-регистрации, если есть) | Легкий подбор пароля | Минимальные требования: длина 8+, буквы+цифры, проверка по словарю |

| 1.3.4 | Отсутствие уведомления о входе с нового устройства | Пользователь не узнает о взломе | Отправлять email/SMS при входе с нового IP/устройства |
| 1.3.5 | Реализация «забыли пароль» (если есть) небезопасна: вопрос-ответ, легкий перебор | Компрометация аккаунта | Использовать email/SMS с одноразовой ссылкой, срок жизни 15 минут |

## 2. Безопасность API (Django REST Framework)

### 2.1 Контроль доступа (авторизация)
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 2.1.1 | Отсутствие проверки прав на уровне ViewSet/APIView | Пользователь может получить/изменить чужие данные (IDOR) | Использовать `get_queryset()` с фильтрацией по текущему пользователю, явно проверять права в `has_object_permission` |
| 2.1.2 | Использование `allow_any` на эндпоинтах, требующих аутентификации | Неавторизованный доступ | Установить `DEFAULT_PERMISSION_CLASSES = (IsAuthenticated,)` и явно открывать только нужные |
| 2.1.3 | Нарушение принципа наименьших привилегий в админке (админ-панель Django) | Менеджеры могут видеть/менять больше, чем нужно | Использовать группы и кастомные разрешения, настраивать `ModelAdmin` с `get_queryset` |
| 2.1.4 | Использование object-level permissions только во views, но не в сигналах или тасках | Обход проверок при фоновых операциях | Вся бизнес-логика должна проходить через сервисы, где проверяются права |

### 2.2 Валидация входных данных
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 2.2.1 | Отсутствует валидация типов полей (например, передача массива вместо числа) | Ошибки приложения, возможное выполнение неожиданного кода | Использовать сериализаторы DRF с явными полями и валидаторами |
| 2.2.2 | Не проверяются поля JSON (например, `delivery_address` в заказе) | Возможна инъекция в PostgreSQL JSON поле или XSS | Валидировать структуру JSON через сериализатор или Pydantic |
| 2.2.3 | Нет ограничений на длину строк в полях | DoS через очень длинные строки | Устанавливать `max_length` в моделях и проверять в сериализаторах |
| 2.2.4 | Отсутствует валидация на бизнес-логику (например, количество товара в корзине не может быть отрицательным) | Некорректные данные, возможные ошибки расчета | Валидация на уровне сериализаторов и бизнес-слоя |
| 2.2.5 | Передача ID объектов, к которым у пользователя нет доступа (например, `store_id` в корзине) | Пользователь может заказать товар из несуществующего магазина | Проверять существование и доступность объекта через `get_object_or_404` с учетом прав |

### 2.3 Безопасность работы с БД (SQL-инъекции)
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 2.3.1 | Использование raw SQL запросов (`raw()`, `execute()`) | Полная компрометация БД | Запретить raw SQL; если крайне необходимо, использовать параметризацию |
| 2.3.2 | Формирование `filter()` с конкатенацией строк | Возможна инъекция через значения, переданные в словарь | Всегда использовать именованные параметры или Q-объекты, избегать f-строк в `filter` |
| 2.3.3 | Отсутствие экранирования в `extra()` или `annotate()` с пользовательскими данными | Инъекция | Избегать `extra`, использовать `annotate` с безопасными выражениями |
| 2.3.4 | Не настроены индексы на часто используемые поля | Медленные запросы, которые могут быть использованы для DoS | Создать индексы на поля, участвующие в фильтрации и сортировке |

### 2.4 Защита от массовых назначений (Mass Assignment)
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 2.4.1 | В сериализаторах не указаны `read_only_fields` для служебных полей (например, `is_active` товара) | Пользователь может изменить флаг активности товара | Явно указывать `read_only_fields` или использовать `write_only` и `read_only` |
| 2.4.2 | Использование `ModelSerializer` без явного перечисления полей (`fields = '__all__'`) | Риск случайного включения чувствительных полей | Всегда перечислять поля явно |
| 2.4.3 | Нет проверки, что поле `user` в заказе устанавливается автоматически, а не из запроса | Пользователь может создать заказ от чужого имени | Устанавливать `user` в `perform_create`, игнорировать входное значение |

## 3. Безопасность данных и конфиденциальность

### 3.1 Хранение персональных данных
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 3.1.1 | Пароли (если есть) хешируются слабым алгоритмом (MD5, SHA1) | Подбор паролей | Использовать PBKDF2, bcrypt или Argon2 (Django по умолчанию использует PBKDF2) |
| 3.1.2 | Номера телефонов, email хранятся в открытом виде | Утечка ПДн | Они должны быть в открытом виде для функционирования, но доступ к ним должен быть строго ограничен. Шифрование при хранении (на уровне диска) |
| 3.1.3 | Логирование полных номеров телефонов и email | Утечка в логи | Логировать только частично (например, последние 4 цифры) или маскировать |
| 3.1.4 | Отсутствие механизма автоматического удаления неактивных пользователей | Избыточное хранение ПДн | Реализовать политику удаления через определенный срок после запроса |
| 3.1.5 | Нет шифрования чувствительных данных в базе (например, номера карт, если хранятся) | Компрометация платежных данных | Никогда не хранить CVV, хранить только маскированные номера. Использовать шифрование на уровне приложения |

### 3.2 Защита при передаче данных
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 3.2.1 | Отсутствует принудительное перенаправление на HTTPS | Перехват данных (MITM) | Включить `SECURE_SSL_REDIRECT = True` в production, настроить HSTS |
| 3.2.2 | Не настроены безопасные куки: `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SECURE_HSTS_SECONDS` | Куки могут быть украдены через нешифрованный канал | Установить все флаги безопасности |
| 3.2.3 | Отсутствует HTTP-заголовок `Content-Security-Policy` | Риск XSS и data injection | Настроить CSP, разрешающий только необходимые источники скриптов и стилей |
| 3.2.4 | Использование устаревших протоколов TLS (TLS 1.0/1.1) | Возможность взлома шифрования | На сервере разрешить только TLS 1.2/1.3 |

### 3.3 Управление доступом к данным в админке
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 3.3.1 | Админ-панель доступна по стандартному URL `/admin` | Легкий поиск цели для атаки | Изменить URL на нестандартный или ограничить доступ по IP |
| 3.3.2 | Отсутствует двухфакторная аутентификация для входа в админку | Учетная запись администратора может быть скомпрометирована | Внедрить 2FA (например, через django-otp) |
| 3.3.3 | В логах админки не фиксируются критические действия (изменение заказа, удаление пользователя) | Отсутствие возможности аудита | Использовать django-admin-audit или кастомное логирование |
| 3.3.4 | Права на модели настроены слишком широко (например, все сотрудники могут удалять заказы) | Внутренние злоупотребления | Настроить группы с детальными правами (просмотр, добавление, изменение, удаление) |

## 4. Защита от веб-атак (OWASP Top 10)

### 4.1 XSS (Cross-Site Scripting)
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 4.1.1 | Отображение пользовательского HTML-контента без экранирования (например, отзывы) | Выполнение произвольного JavaScript | Использовать `|escape` или `|safe` только если контент доверенный. В React/Next.js – избегать `dangerouslySetInnerHTML` |
| 4.1.2 | Встраивание данных из URL в DOM без санитайзинга | XSS через параметры | Всегда использовать методы безопасной вставки (текстовые ноды, атрибуты) |
| 4.1.3 | Использование `innerHTML` в клиентском коде с данными из API | XSS | Заменить на `innerText` или `textContent`, либо использовать DOMPurify |
| 4.1.4 | Не настроена CSP (Content-Security-Policy) | Облегчает выполнение инъекций | Установить строгую CSP, запрещающую inline скрипты |

### 4.2 CSRF (Cross-Site Request Forgery)
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 4.2.1 | Django CSRF middleware отключен для API | Злоумышленник может выполнить действия от имени пользователя | Включить CSRF для всех state-changing методов (POST, PUT, DELETE) |
| 4.2.2 | В Next.js не используются CSRF токены для форм, отправляемых на Django | Атака CSRF возможна | Использовать `getCsrfToken` из next-auth или передавать CSRF cookie в заголовке `X-CSRFToken` |
| 4.2.3 | CSRF токены не проверяются для AJAX запросов | Атака через AJAX | Убедиться, что все запросы (включая fetch/axios) отправляют CSRF токен |
| 4.2.4 | Отсутствует защита от CSRF для методов, изменяющих состояние, но использующих GET | Использование GET для небезопасных операций | Все операции, изменяющие данные, должны быть только POST/PUT/DELETE |

### 4.7 Недостаточное логирование и мониторинг

| 4.7.2 | Не логируются неудачные попытки входа, попытки сброса пароля | Невозможно обнаружить атаку перебора | Логировать такие события в отдельный файл или Sentry |

## 5. Безопасность платежей и интеграций

### 5.1 Интеграция с платежными системами
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 5.1.1 | Не используется HTTPS для взаимодействия с платежным шлюзом | Перехват данных | Всегда использовать HTTPS, проверять сертификаты |
| 5.1.2 | Отсутствие проверки подписи webhook уведомлений | Подделка статуса оплаты | Проверять подпись запроса от платежной системы |
| 5.1.3 | Хранение номера карты, CVV в базе | Нарушение PCI DSS | Никогда не хранить CVV, для повторных платежей использовать токены шлюза |
| 5.1.4 | Нет защиты от повторного использования успешного уведомления (idempotency) | Двойное списание | Реализовать идемпотентность по ID транзакции |
| 5.1.5 | Платежные данные передаются через фронтенд на бэкенд (вместо прямого взаимодействия с ПС) | Повышенный риск утечки | Использовать прямую интеграцию с ПС через JS SDK, чтобы данные карты не проходили через сервер |

### 5.2 Интеграция с внешними API (SMS, карты, CRM)
| # | Уязвимость / Что проверить | Потенциальные последствия | Рекомендации |
|---|----------------------------|--------------------------|--------------|
| 5.2.1 | API ключи хранятся в коде или .env, но доступны в интернете (например, через frontend) | Утечка ключей | Все ключи только на бэкенде, фронтенд получает только публичные ключи |

## Заключение

Данный чек-лист охватывает ключевые области безопасности интернет-магазина. Каждый пункт должен быть проверен на соответствие в текущей реализации проекта. Рекомендуется:

1. Провести аудит кода по каждому из пунктов.
2. Внедрить автоматические проверки в CI/CD для предотвращения регрессий.
3. Регулярно обновлять зависимости и сканировать образы.
4. Провести внешний пентест перед запуском.
5. Настроить мониторинг и алерты на подозрительные события (много неудачных входов, необычные запросы).

Если какой-либо пункт не применим (например, нет приема платежей онлайн), его можно исключить, но с осознанием риска.

После устранения найденных проблем, проект можно считать защищенным на уровне, достаточном для запуска.
